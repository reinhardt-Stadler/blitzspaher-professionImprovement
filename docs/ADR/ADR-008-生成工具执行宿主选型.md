# ADR-008：生成工具的执行宿主——独立容器

> 状态：**已决定**（2026-11-15）
> 关联：`ADR-006`（执行面扩展与动态工具安全边界）、`45-RA3`（RA-3.2）、`13-器官` §1.8
> 关闭：**OQ-15**

## 背景（Context）

`kernel/toolgen/review.ts` 的七条规则是**文本级**检查。它能挡住直接 `import fs`、拼 shell、
`eval` 这类写法，但挡不住字符串拼接构模块名、`globalThis["fe"+"tch"]`、压缩后解码执行。

所以规格把"生成代码在哪跑"单列为 OQ-15，并要求**至少两个候选实测比较**（ADR-000 第 3 条）。
本期实测了两个候选，其中一个被淘汰、一个通过。

## 决策（Decision）

**生成代码在一次性 Docker 容器里执行，网络只接实验室网络。**

```
docker run --rm \
  --network=<lab net>          # 出网不通；实验室内部互通
  --memory=256m --cpus=0.5     # 资源上限（实测 cgroup 生效）
  -v <tmp>:/work:ro            # 代码只读挂载（实测 Read-only file system）
  -w /work --entrypoint node <image> /work/bootstrap.mjs
```

三条配套约束：

1. **代码只读**：生成代码挂 `:ro`，容器内无法改自己、无法写盘留东西。
2. **ctx 由 bootstrap 注入**：`bootstrap.mjs` 是**我们写的**固定文件（不是生成的），
   它构造 `ctx.http` 并在每次请求前校验 host 是否在 `allowedTargets` 内，再调用生成的
   `run(ctx, args)`，把结果以 JSON 打到 stdout。生成代码没有别的 IO 入口。
3. **一次性**：`--rm`，每次调用一个新容器，不保留状态。

## 备选方案（Alternatives）

### 候选 1：子进程 + Node 权限模型 —— **实测淘汰**

`node --permission`（本机 v22.22.2）实测：

| 模块 | 结果 |
| --- | --- |
| `fs` | 拒（`ERR_ACCESS_DENIED`） |
| `child_process` | 拒（`ERR_ACCESS_DENIED`） |
| **`net`** | **放行**（连 1.1.1.1 未被拦，只有网络本身超时） |

淘汰理由命中规格给出的淘汰线："**无法禁出网即淘汰**"。生成代码能自己连任意主机，
目标授权形同虚设。

### 候选 2：独立容器 —— **实测通过**

见下节证据。10 项检测全 PASS。

### 候选 3：WASM —— **未实测，按淘汰线预判**

WASI 没有 socket 接口。要让 WASM 里的代码发 HTTP，只有宿主代发一条路——
那就退化成"宿主按指令代发请求"，而这正是 **probe spec（声明式）已经做的事**。
换言之 WASM 对"执行任意生成代码"这个形态提供不了网络隔离，只是把问题挪回宿主侧。
因此没有测：它的结论不改变决策。

## 最小实验 / 证据

执行：`bash deploy/ra32-host-isolation.sh`（WSL 内，docker 29.1.3，镜像 `blitzspaher-agent:0.1`）

| # | 检测 | 结果 | 原始输出 |
| --- | --- | --- | --- |
| 1 | 宿主机直连基线 | PASS | `http=200`（证明测法有效，排除"本来就没网"的假通过） |
| 2 | 默认桥接能出网（对照组） | PASS | `http=200` |
| 3 | `--network=none` 不能出网 | PASS | `curl: (6) Could not resolve host` / exit=6 |
| 4 | 实验室网络出网不通 | PASS | exit=6 |
| 5 | 实验室网络靶场可达 | PASS | `http://bz-target-fastjson:8090/ -> http=200` |
| 6 | 只读挂载生效 | PASS | `cannot create /work/ra32.txt: Read-only file system` |
| 7 | 128MB 内存上限 | PASS | `cgroup=134217728` |
| 8 | 启动延迟 | PASS | 252 / 272 / 281 ms（淘汰线 2s） |
| 9 | node 可在容器内执行 | PASS | `node -e 'console.log(1+1)'` -> `2` |
| 10 | **出网套接字在内核层被拒** | PASS | `BLOCKED:ENETUNREACH` |

第 10 项是决定性证据：`ENETUNREACH` 是内核返回的"无路由"，不是代码自律，
也不是代理改写。这是规格要求的"物理证据"。

第 1 项同样关键：本机只有走代理才能出网，容器内没有代理。若不做宿主机直连基线，
第 3 项会**假通过**——看起来挡住了，其实是压根没网。

## 后果（Consequences）

### 正面

- 代码形态的工具生成可以**解禁**：`ToolRegistration.executable` 从恒 `false` 改为按
  "审查通过 + 人工确认 + 宿主可用"三条件判定。
- 与既有授权模型不冲突：容器网络边界是物理的，不依赖 `review.ts` 的文本规则质量。
- 可复用现有部署形态（镜像、lab 网络已就绪）。

### 负面 / 成本

- **网络粒度是"实验室内部"，不是"单个授权目标"**。生成工具能连 `pentest-net` 里的
  其它靶场容器，比"只能连本次授权那个"宽。要收紧到单目标，需要每次执行动态建网络
  （实测启动 252ms，再叠加建网络开销），本期不做，登记为后续优化。
- **每次工具调用固定 ~250ms 启动开销**。对单次调用无感，但循环里几十次会累积；
  预算按"调用次数"计时不受影响，按"耗时"计时需计入。
- 需要镜像里存在 node 运行时；镜像变更会牵连执行宿主。
- 容器逃逸漏洞成为新的攻击面（生成代码是不可信输入）。缓解：非 root 用户（镜像内
  `agent` uid 10001）、只读挂载、`--memory`/`--cpus` 限制、不挂 docker socket。

### 对既有代码的影响

| 位置 | 改动 |
| --- | --- |
| `ToolRegistration.executable` | 从恒 `false` 改为三条件判定 |
| `NOT_EXECUTABLE_REASON` | 改为"宿主未就绪时"才为真 |
| `45-RA3` §RA-3.2 | 候选比较结论回填 |
| `4工作项与路线图` OQ-15 | 关闭 |
