# ADR-007：状态外部化的存储形态

- 状态：**已决定**（纸面对比，未实测；实测留给实现阶段）
- 日期：2026-11-10
- 决策者：组内（用户确认折中档范围后落地）
- 对应设计：`design/agent-refactor/20-难点-宿主与状态.md` B1、`2规格/02-内核与状态.md` §2.4
- 关联需求/验收：FR-TASK-02、P1（全量档）、C01–C04

## 背景（Context）

ADR-005 定了"内核状态必须可序列化、可恢复，且恢复点与 `audit.jsonl` 的事件序对齐"，
但没有定**存到哪、怎么存**。需要回答两个问题：

1. 状态的权威载体是什么？（事件日志 / 数据库 / 全量快照）
2. 恢复时怎么和已有审计日志对上？（本项目已有 append-only 的 `audit.jsonl`）

约束条件：

- 恢复点必须能与审计事件序**严格对齐**，否则无法判断"状态与证据是否一致"；
- 恢复后**不得重放**已发出未回收的调用（工具可能有副作用）；
- 不引入额外运行时依赖（容器内 Node 24，无构建步骤）。

候选方案：事件日志 + 快照 / SQLite / 纯全量快照。

## 决策（Decision）

> **`state.jsonl`（append-only，权威）+ `snapshot-<seq>.json`（加速恢复，留最近 3 份）。
> 事件与审计共用同一个单调 `seq`，双向对账；`pending` 调用恢复后标 `UNKNOWN_OUTCOME` 且不重放。**

四条具体约定：

1. **权威在日志**：快照只是缓存，丢了可以从日志重放；日志丢了则状态不可信。
2. **同序号对齐**：每条审计事件带 `stateSeq`，恢复时比对 `max(stateSeq)`，两个方向的缺口码不同。
3. **幂等**：每个 reducer 分支必须能重复应用同一 `seq` 而不改变状态——重放必然可能重复。
4. **不重放副作用**：`pending` 只标记不重发。

## 备选方案（Alternatives）

| 方案 | 优点 | 缺点 / 淘汰原因 |
| --- | --- | --- |
| **JSONL + 快照（采用）** | 与 `audit.jsonl` 同构，同 `seq` 对齐最自然；零依赖；可人工阅读 | 重放要写幂等分支；文件随事件增长（用快照+裁剪缓解） |
| SQLite 单文件 | 事务、查询、并发都省心；容器内 Node 自带 `node:sqlite` | **状态与审计变成两条真相线**，两写不一致需额外机制保证；审计仍是 JSONL，等于维护两套存储 |
| 纯全量快照 | 实现最简单，无重放 | 写放大严重（长任务每步几百 KB）；**丢失"状态怎么变过来的"这条过程证据** |

## 最小实验 / 证据

**未做实测，属纸面对比。** 依据是一条硬约束推导：ADR-005 要求"恢复点与审计事件序对齐"，
而 `audit.jsonl` 已是 append-only + 单调序号，用同一套机制最省心；数据库方案要把两种存储对齐，
成本高于收益。

实测在实现阶段（RA-1.6，全量档）完成，判定门槛三条：
往返一致 / `pending` 不重放 / 删一行即产 `GAP_STATE_TRUNCATED`。
**实测不过则重开本 ADR。**

## 后果（Consequences）

### 正面

1. 状态与证据同源同序，`reconstruct` 能直接判断"状态与审计是否对得上"。
2. 零依赖、可人工复核，与项目"证据可复现"的整体取向一致。
3. 状态文件可随证据包一起交付，复核者不需要装数据库。

### 负面 / 成本

1. 每个 reducer 分支都要写成幂等，实现约束比"直接改对象"强。
2. 日志会增长，需要快照 + 裁剪策略（保留最近 3 份，长度按事件数而非时间）。
3. 并发写不安全（单进程假设）；多 Agent 时需重开。
