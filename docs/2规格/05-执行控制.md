## 5.1 判定序（唯一入口）

| # | 检查 | 拒绝码 | 备注 |
| --- | --- | --- | --- |
| 0 | `arm=off` 基线 | `ARM_OFF_BASELINE` | 只观测不裁决，落同构 decision |
| 1 | 已停止 | `STOPPED` | — |
| 2 | **授权档位** | `LEVEL_INSUFFICIENT` | 排在工具白名单之前，使归因指向"档位不足" |
| 3 | 预算（两本账） | `PHASE_BUDGET_EXHAUSTED` / `BUDGET_EXCEEDED` | 按工具类别扣对应账本 |
| 4 | 工具注册表（全量，含内置） | `TOOL_NOT_AUTHORIZED` / `BUILTIN_TOOL_DENIED` | 默认拒绝，未登记即拒 |
| 5 | 目标授权 | `TARGET_NOT_AUTHORIZED` | 精确主机匹配 |
| 6 | 参数约束 | `PARAM_INVALID` | Schema + 跨度限额 |
| 7 | 重复判定（分级） | `DUPLICATE_CALL` | 分三级，见 §5.4 |
| 8 | 高危 / 提权 | 返回 `needsHuman` | 语义为"申请提档"，不是逐次弹窗 |

**档位放在第 2 位而非第 4 位**：拒绝归因才会是"这档位不允许这类动作"（提档可解），
而不是"工具没授权"（要改 policy）。两者的整改动作完全不同。

**同时不满足时记双码**：档位与预算同时不足，只报 `LEVEL_INSUFFICIENT` 会把人引去提档——
提完档再跑一步又停，因为预算也尽了，整改方向被指错一次。
判定序仍按 2 → 3 短路（只判一次，不重复算账），但 `decision` 事件必须带 `codes: string[]`：
`code` 保留首个为主因，其余落 `codes` 为并因，报告同时列出。
**新增拒绝码**：`OUT_OF_WINDOW`（超出 `policy.timeWindow`），并入第 5 步目标授权一起校验。

## 5.2 授权档位

| 档位 | 允许的工具类别 | 典型场景 |
| --- | --- | --- |
| `recon` | scanner / web_probe / knowledge / evidence_collector / report | 只做信息收集 |
| `verify` | 追加 vulnerability_check | 常规验证任务（默认） |
| `callback` | 追加 callback（监听与回连类） | 需要证明可利用性 |
| `toolgen` | 追加 generated（生成工具注册与执行） | 需要造新工具 |

**规则**：档位是累积的，单向授予；提升需一次人工确认（`/pentest-escalate`）；
撤销即时生效且不可恢复（`/pentest-revoke`）。档位进 `TaskPolicy`，参与 `configHashV2` 的 `policyShape`。

## 5.3 两本账

| 段 | 内容 |
| --- | --- |
| 实现手段 | `BudgetTracker`（全局四维，不动）+ `PhaseAllocator`（explore / verify 两本配额） |
| 达成指标 | 前期信息收集不吃掉后期验证预算；报告分别给出两本账余额与消耗 |
| 依赖决策 | `design/agent-refactor/01-起因与目标.md` §5（预算改阶段分配） |
| 状态 | 🟡 → `SEC-BUDGET-01` / `R9` |

**类别到账本的映射**（单一来源：`TOOL_REGISTRY.account`）：

| 账本 | 工具类别 | 用尽时行为 |
| --- | --- | --- |
| `explore` | scanner / web_probe / knowledge | 提示收束，验证类仍可用 |
| `verify` | vulnerability_check / callback / generated | 提示收束并建议出报告 |

**两份水位都要报**：`level()` 只看全局 `tightest`，阶段配额耗尽时仍返回 `normal`——
报告必须单列"阶段配额耗尽"，不能把配额塞进 `tightest`（会让全局语义混乱）。

### 5.3.1 跨账支取（单向，有上限）

两本账若完全隔离，探出线索却没钱验证——真实渗透里最值钱的动作会被自己的预算结构挡住。

| 项 | 规则 |
| --- | --- |
| 方向 | **只能 explore → verify**，反向禁止 |
| 触发 | 出现新的 `cve` 候选事实，且该候选**尚无**对应 `cve_check` 调用 |
| 额度 | 单次 ≤ verify 剩余配额的 20%；全任务累计 ≤ 3 次 |
| 记账 | verify 记支取、explore 记出让；报告"效率"组单列支取次数与额度 |
| 审计 | 落 `budget_transfer`（`from` / `to` / `amount` / `triggerFactKey`） |

**为什么单向**：探索是可选的，验证是交付必需的。反向借会让信息收集提前枯竭，
最后连"有什么可验证"都答不出来。

**为什么必须有上限**：无上限的支取等于取消两本账，退回单池。20% 与 3 次是初值，
首次试跑后冻结（同 OQ-09 口径）。

**支取不改变判定序**：第 3 步仍按工具类别扣账，"借来的额度"只是让 verify 账的余额不早归零，
不新增拒绝码。

## 5.4 重复判定分级

| 情形 | 裁决 | 记账 |
| --- | --- | --- |
| 完全同参**且目标状态版本相同** | `deny DUPLICATE_CALL` | 不计 |
| 同工具同参数，但**目标状态版本已变** | `allow` + 标 `RESURRECTED_RETRY` | 计 explore |
| 同工具同目标、不同参 | `allow` + 标 `EXPLORATORY_RETRY` | 计 explore |
| 同工具不同目标 | `allow` | 计 explore |

理由：一律拒会逼模型不敢探索；一律放会刷调用量。分级后"探索"有账可记、有数可查。

**指纹 = `hash(工具名 + 参数 + targetStateVersion)`**，版本定义见 §5.4.1。

### 5.4.1 目标状态版本（`targetStateVersion`）

每个目标一个自增整数，落 `KernelState`。**只在两件事发生时 +1**：

| 触发 | 为什么算"状态变了" |
| --- | --- |
| 该目标出现 `target_unreachable`（任一工具连续 2 次） | 主机可能在重启；重启前的"连不上"不能作为"以后也不必再试"的依据 |
| 该目标新增 `port` / `service` 事实 | 服务集合变了，同一条探测在新端口上可能给出不同结果 |

**不加版本的情况**：时间过去、模型换了措辞、上次结论是 `INCONCLUSIVE`。
这三种都不构成"重试有理由"，版本不变，重复判定照拦。

**为什么用版本而不是"申诉"**：申诉要人判、要留通道、要防滥用。版本是**事实驱动**的——
目标真变了才放行，没变一律拦。模型不需要说服任何人，也不需要一条"求情"通路。

### 5.4.2 重复拦截与停止的界线

单次重复只拒绝，不进停止计数；只有 `DUPLICATE_CALL` 累计超阈值才触发停止（`04` §4.6）。
`RESURRECTED_RETRY` **不计入**重复计数——它本来就因为目标变了才被放行。

## 5.5 审计 schema

| 段 | 内容 |
| --- | --- |
| 实现手段 | `audit-schema.ts` 定义 `AuditEventKind` + 每类必填字段 + `validateEvent()` |
| 达成指标 | contract test：每种 kind 一条 golden JSON，四个消费者都能解析 |
| 状态 | 🟡 → `SEC-AUDIT-01` / `P9` |

**现有 6 类 kind**：`decision` / `execution` / `human` / `stop` / `budget_warn` / `run_end`。
**本期新增**：`plan`（计划变更）、`hypothesis`（假设状态迁移，含 `reopen`）、`inject`（系统注入）、
`callback`（回连事件）、`toolgen`（生成工具注册与审查）、`memory_pruned`（裁剪）、
`budget_transfer`（跨账支取，§5.3.1）、`tool_fallback`（工具降级，`06` §6.7）。

**新增 kind 五步清单**（缺一不合入）：schema → reconstruct（是否进 timeline / 是否算缺口）→
report（是否进未执行项/故障/覆盖）→ evidence-collector（是否独立证据类型 + manifest 版本）→ contract test。

> 为什么必须 contract test：`kind` 是联合类型但消费方用 `===` 比较，新增 kind **不报编译错**，只静默不被消费。

## 5.6 旁路封堵

| 段 | 内容 |
| --- | --- |
| 实现手段 | `ALLOWED_TOOL_NAMES = 注册表 ∪ {pentest_report, evidence_collector}`；不在集合内一律 `deny BUILTIN_TOOL_DENIED` |
| 达成指标 | 容器内直接 `curl` 未授权目标 0 次到达执行层，且有 `decision` 记录 |
| 依赖决策 | **⏸ 实测 Q2**（内置工具能否禁用）+ Q6（block 后 `tool_result` 是否触发） |
| 状态 | ⏸ A/B/C 三分支见 `40-RA0-实测与漏斗.md` |

**分支 C 是风险点**：若 `tool_call` 事件只对注册工具触发，漏斗方案整体失效，
必须回到配置层禁用或改为宿主级包装。这条要单列进风险表（已登记）。

## 5.7 审计与观测解耦

`arm=off` 只关裁决、不关日志。这条不能因为新增档位/两本账而破坏——
否则 OFF 组没有可比基线，EXT-DIFF 全部作废。
