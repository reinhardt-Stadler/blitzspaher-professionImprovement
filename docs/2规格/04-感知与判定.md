# 规格 04 · 感知与判定规格（L2 认知）

> **层**：L2 认知 | 覆盖：TargetModel、覆盖率、三态判定、停止决策、与离线判定的分工 | **服务需求：FR-AGENT-01、FR-AGENT-04、SEC-STOP-01**
> 上位：`03-规划记忆与任务.md`　下位：`05-执行控制.md`
> 对应设计：`12-器官-状态建模与执行判定.md` §1.6/§1.7

## 4.1 同源投影（一切感知的前提）

| 段 | 内容 |
| --- | --- |
| 实现手段 | 一份 `Observation` 只解析一次，同时产出 `summary`（给模型）、`Fact[]`（给判定层）、`TargetModel` 增量（给认知层） |
| 达成指标 | 单测断言"投影 ⊆ 台账"：图里每个节点都能在 ledger 找到对应事实 |
| 依赖决策 | 无 |
| 状态 | 🟡 → `FR-AGENT-01` / `P4` |

**为什么是硬约束**：若台账与图各写一套正则，同一次调用会得到互相矛盾的结论
（"台账说发现 8080，图里没有"），这种矛盾在报告里无法审计。

## 4.2 TargetModel

| 段 | 内容 |
| --- | --- |
| 实现手段 | 六类节点（host/port/service/component/cve/path）+ 四类边（`has_port`/`identified_as`/`serves`/`vulnerable_to`） |
| 达成指标 | 用现有 `audit/observations/` 真实记录回放，人工核对 ≥3 个节点的边成立 |
| 依赖决策 | 硬约束：封闭枚举不动（`design/agent-refactor/05` §5） |
| 状态 | 🟡 → `FR-AGENT-01` / `P4` |

节点与边的完整投影表见 `12-器官-状态建模与执行判定.md` §1.6。两条实现纪律：

1. **不做替代**：验收判定（R4 召回率、`phaseOf`、报告四态）继续读扁平 `ledger`，图只服务规划与覆盖率。
2. **不落盘**：`targetModel` 是派生字段，恢复时由 `ledger` 重算（`02-内核与状态.md` §2.2）。

**派生阶段的代价（写清楚，免得被当 bug 修）**：`phase` 由 `phaseOf(ledger)` 算，**不由模型宣布**。
含义是：事实没进来，阶段就不动。模型觉得"我明明收集完了"，只要台账里没有对应的 `port` / `service` 事实，
它仍停在 recon。这是有意的——阶段若可由模型宣布，阶段就失去约束力，报告里的"已执行范围"也变成模型的自述。
要改的是解析器或探测方式，不是让模型改阶段。

## 4.3 覆盖率

| 指标 | 定义 | 数据来源 | 用途 |
| --- | --- | --- | --- |
| 端口覆盖率 | 已扫端口 ÷ **授权端口范围**（`policy.portScope`，由端口跨度限额推出） | `TaskPolicy` + nmap 事实 | 判断信息收集是否收敛 |
| 组件识别率 | 有 `identified_as` 的端口 / 开放端口 | nmap + http_probe | 判断能否进入漏洞验证 |
| 验证完成率 | 有结论的 `cve` 节点 / 候选 `cve` 节点 | cve_check + 知识候选 | 报告的"未覆盖项"依据 |

**分母只能来自授权侧，不能来自探测结果**。若写"已扫端口 / 已知端口"，而"已知端口"只有扫过才知道，
这就是循环定义——分母随扫描进度增长，覆盖率永远是 100% 与 0% 之间的任意值，指标失效。
`policy.portScope` 在任务确认时即固定，不随扫描变化。

`version` 缺失时单列"版本未知"计数——**不得把版本未知当成"无漏洞"**。
**探测不完整**（`policy.portScope` 未扫完、`target_unreachable` 已计 2 次）单列第三类，
既不进"有漏洞"也不进"无漏洞"——清单 3.4 的"一次扫描没发现开放端口不等于没有服务"，说的就是这个。

## 4.4 三态判定（在线）

| 段 | 内容 |
| --- | --- |
| 实现手段 | `verdict(input) → StepVerdict`，六行判定表，纯函数 |
| 达成指标 | 六行逐行用例；`OBS-CASE-003` 四类异常落到不同分支 |
| 状态 | 🟡 → `FR-AGENT-04` / `P2` |

```ts
export type StepVerdict =
  | { kind: "advance"; hypothesisId: string | null; note: string }
  | { kind: "retry_change";
      reason: "inconclusive" | "partial" | "fingerprint_unknown" | "target_unreachable";
      allowedVariations: Array<"path" | "content_type" | "port"> }
  | { kind: "abandon"; reason: "retry_exhausted" | "tool_unavailable" | "contradicted" | "no_capability" };
```

判定**先看 `errorKind`，再看结论**——顺序颠倒会把"目标在重启"判成"工具坏了"：

| 序 | 条件 | 判定 | 副作用 |
| --- | --- | --- | --- |
| 1 | `errorKind=target_unreachable` | `retry_change(target_unreachable)`，换入口或端口 | **不动 `toolHealth`**；连续 2 次才 `abandon(tool_unavailable)`，且 `toolHealth=degraded`（不是 `unavailable`） |
| 2 | `errorKind ∈ {tool_missing, tool_crash}` 且连续 ≥2 | `abandon(tool_unavailable)` | `toolHealth=unavailable`，触发 `06` §6.7 降级阶梯 |
| 3 | `errorKind ∈ {timeout, param_rejected}` 且 `attempts<2` | `retry_change` | 必须换参，同参被 I3 拦 |
| 4 | `errorKind=parse_failed` | `advance(note="解析缺口")` | 落 `GAP_PARSE_FAILED`，**不重试** |
| 5 | 结论 `CONFIRMED` / `NOT_CONFIRMED` | `advance` | — |
| 6 | `INCONCLUSIVE` 且 `attempts < 2` | `retry_change` | 必须换参数，同参重发被 I3 拦 |
| 7 | `INCONCLUSIVE` 且达上限 | `abandon(retry_exhausted)` | — |
| 8 | 新事实与假设 `basis` 矛盾 | `abandon(contradicted)` | — |
| 9 | **假设无可用验证手段**（无 probe spec） | `abandon(no_capability)`，假设置 `unverifiable` | 进"未覆盖项"，原因码 `no_probe_spec`；**不得**降级成 `NOT_CONFIRMED` |
| 10 | **组件无法识别到已知条目** | `abandon(no_capability)`，假设置 `unverifiable` | 原因码 `unknown_component`；不套用任何 CVE |

**`parse_failed` 为什么不重试**：重发同一请求只会得到同一份解析不了的输出。要修的是解析器，不是重跑。
**`target_unreachable` 为什么不清 `toolHealth`**：靶场重启、容器冷启动都是常态，把工具标成报废之后，
后续所有任务都会降级到一个残缺的工具集，而这个"报废"是假的。

**`verdict` 的职权边界（放内核就必须写死，否则它会悄悄长成第二个 planner）**：

| 它能判 | 它不能判 |
| --- | --- |
| 当前这条假设：重试 / 换路 / 放弃 | **下一条假设是哪个**（归模型） |
| 重试时可以换哪几个**维度** | 具体换成什么**值**（归模型） |
| 工具是否应标降级 | 是否该换工具（归模型，受 `06` §6.7 约束） |

放内核的理由是"避免两个 planner"，**不是**"内核也会规划"。
越界判据：`StepVerdict` 三个分支里若出现工具名、参数值、假设 ID 排序，即为越界。
类型层现在拦得住（无这些字段），以后改的时候别往里加。

**只给维度不给参数**：`allowedVariations` 声明"可以换 path / content-type / port"，
具体换成什么由模型决定。这是约束，不是指令（`design/agent-refactor/05` §2）。

## 4.5 与离线判定的分工（必须分清）

| 判定 | 问题 | 位置 | 用途 | 是否在线 |
| --- | --- | --- | --- | --- |
| `assess()` | 这次调用**有没有新增事实** | `evidence.ts`（已有） | 无效调用率、R4、"无新增证据"停止条件 | 否，离线重建 |
| `verdict()` | 下一步**该不该继续这条假设** | `kernel/verdict.ts`（新） | 重试/换路/放弃 | 是 |
| `decideStop()` | 整条任务**要不要停** | `kernel/decision.ts`（新） | 六个停止条件 | 是 |

三者混用会互相污染：例如用 `assess()` 判"该不该重试"，会把"这次没新事实"误当成"这个假设错了"。

## 4.6 停止决策

| 段 | 内容 |
| --- | --- |
| 实现手段 | `decideStop(state) → StopReason \| null`，七个条件各一行（六中止 + 一完成） |
| 达成指标 | 七条件逐条用例；停止原因与审计终态事件一致；`objective_met` 与其余六条在报告中分组呈现 |
| 状态 | 🟡 → `SEC-STOP-01` / `P1` |

| 条件 | 判定依据 | 与其他模块的边界 |
| --- | --- | --- |
| 预算耗尽 | `PhaseAllocator` 两本账任一归零或水位 ≥1.0 | 预算模块只报水位，不判"停" |
| 连续失败 | `counters.consecutiveFailures ≥ 2` | 工具健康标记由 `verdict` 写 |
| 重复调用 | 判定层 `DUPLICATE_CALL` 计数超阈值 | 单次重复只是拒绝，不停止 |
| 无新增证据 | 连续 N 次 `assess=invalid_no_new_fact` | 需要离线判定结果，故用事件回灌 |
| 用户撤销 | `user_command: revoke` | 立即停 |
| 边界阻断 | 单次任务内 `TARGET_NOT_AUTHORIZED` 计数超阈值 | 一次越界只是拒绝，不停止 |
| **目标达成** | 假设全部闭环 **且** 覆盖率达标（判据见下） | 唯一的**正常完成**，产出 `objective_met` |

**七条件分两类，报告里必须分开写**：第 1–6 条是**中止**（资源没了 / 出事了 / 用户喊停），第 7 条是**完成**。
混成一样的后果很具体：正常跑完的任务最后一定停在"无新增证据"上，报告读起来像"没查出东西"；
且 `3验收/02` R1 的"非预期停止率"永远冻结不了口径——"预期"这个状态根本没被建模。

**`objective_met` 的判据（两条同时成立，缺一不算）**：

1. 假设清单：每条 `status ∈ {confirmed, refuted, unverifiable, abandoned}`，无 `open` / `collecting`，
   **且不存在"已 `reopen` 但仍未闭环"的假设**（`03` §3.3.1）——重开过又没结论的，不能算完；
2. 覆盖率：端口覆盖率与组件识别率均 ≥ `policy.coverageTarget`（**数值首次试跑后冻结，同 OQ-09**）。

只满足第 2 条不叫达成——扫完了却没有一条假设闭环，说明计划没落到假设上，那是"跑完了"不是"做完了"。
反过来只满足第 1 条也不叫达成：三条假设全闭环但端口才扫了十分之一，结论覆盖不了目标。

**七条件集中在 `decision.ts` 后，`security-control.ts` 不再自己 `halt()`**，
只在上报"预算耗尽"时由内核判停——否则同一件事有两个决策点。
