## 1. 三个概念必须分开

工具调用被问到的其实是三个不同问题，混在一个字段里就无法分别回答：

| 概念 | 回答 | 由谁决定 | 变化时机 |
| --- | --- | --- | --- |
| `available` | 这个环境里**有没有**这个工具 | 环境探测（容器内是否装了 nmap / curl） | 环境变化时 |
| `allowed` | 本任务**是否授权**调用它 | 用户确认的 `TaskPolicy` | 任务开始时；运行中只缩不扩 |
| `capability` | 这次调用属于**哪类能力**、授予了没有 | 工具的 `mode.capability` × `policy.capabilities` | 同 `allowed` |

**为什么必须分**：三者不分，"工具没装"和"没授权"在调用侧表现一样（都是失败），
模型分不清该换工具还是该申请授权。前者要降级，后者要澄清，处置方向相反。

`available = false` 导致的失败**不计入无效调用率**——那是环境能力问题，不是模型判断失误。

## 2. 工具侧：一个工具可以有多个操作模式

**不能只靠工具名表达约束。** 同一个 `nmap`，`scan` 与 `version_scan` 的风险和参数约束不同。

| 字段 | 语义 | 约束 |
| --- | --- | --- |
| `ToolMode.id` | 模式标识，如 `nmap.scan` | 全局唯一 |
| `ToolMode.capability` | 该模式属于哪类能力 | 单值；一个模式只属于一类 |
| `ToolMode.risk` | `read_only` / `intrusive` / `destructive` | 决定缺省是否放行 |
| `ToolMode.parameters` | **模式级**参数约束 | 端口跨度、速率、payload 形态都写在这里 |
| `ToolMeta.effects` | 外部副作用类型 | 闭环清单据此枚举入口 |

参数约束**按模式走**，不按工具走：`nmap.scan` 的端口跨度上限与 `nmap.version_scan` 可以不同。

## 3. 任务侧：授权是能力集合 + 模式白名单

```ts
interface ToolGrant {
  tool: string;
  modes?: string[];    // 缺省行为见 §4 表
}

interface TaskPolicy {
  capabilities: Capability[];   // 能力集合，非等级；默认空集
  grants: ToolGrant[];
  allowedTargets: string[];
  budget: { maxCalls: number; maxRuntimeMs: number; perToolTimeoutMs: number };
}
```

**组合规则**：一次调用必须同时通过五道，任一不过即拒。

| 序 | 检查 | 拒绝码 |
| --- | --- | --- |
| 1 | 工具在注册表且出现在 `grants` | `TOOL_NOT_AUTHORIZED` |
| 2 | `mode.capability ∈ policy.capabilities` | `CAPABILITY_NOT_GRANTED` |
| 3 | `grants.modes` 指定时 `mode.id` 在其中；缺省时 `mode.risk = read_only` | `MODE_NOT_AUTHORIZED` |
| 4 | 参数符合 `mode.parameters` | `PARAM_INVALID` |
| 5 | `targetParam` 非空时提取出主机且在白名单 | `TARGET_NOT_AUTHORIZED` / `PARAM_INVALID` |

**为什么缺省只放行只读模式**：`modes` 不写全就给全部权限，等于把"忘写"变成"放行"。
缺省 = 只读，是默认拒绝在模式层的延伸。

## 4. 默认行为表（写死，不许实现侧自行解释）

| 情形 | 行为 | 码 | 计无效调用 |
| --- | --- | --- | --- |
| 工具未注册 | 拒 | `TOOL_NOT_AUTHORIZED` | 否 |
| 工具已注册但未授权 | 拒 | `TOOL_NOT_AUTHORIZED` | 否 |
| 能力未授予 | 拒 | `CAPABILITY_NOT_GRANTED` | 否 |
| 模式未授权 / 缺省且非只读 | 拒 | `MODE_NOT_AUTHORIZED` | 否 |
| 声明了 `targetParam` 但取不到主机 | 拒 | `PARAM_INVALID` | 否 |
| 参数不符合模式 schema | 拒 | `PARAM_INVALID` | 否 |
| 目标不在白名单 | 拒 | `TARGET_NOT_AUTHORIZED` | 否 |
| `available = false` | 拒 | `TOOL_UNAVAILABLE` | **否** |
| 同参重发 | 拒 | `DUPLICATE_CALL` | **是** |

**所有被拒的调用都必须落 `decision` 事件**（含 `toolCallId` / `code` / `args`）。
拒绝不产生外部副作用，但拒绝本身必须可审计——否则无法证明"拦住了"。

**归因要分得开**：内置工具被拦记 `BUILTIN_TOOL_DENIED`，自研工具未注册记 `TOOL_NOT_AUTHORIZED`，
两者都属"第 1 道不过"，但整改动作不同——前者要改白名单策略，后者要改注册表。混成一个码，
报告里就分不清"策略没收口"和"工具没登记"。
