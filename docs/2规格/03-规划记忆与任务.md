## 3.1 任务解析与 policy

| 段 | 内容 |
| --- | --- |
| 实现手段 | 规则先行（显式目标/预算/范围）→ 未命中字段交 LLM 抽 `Partial<TaskDraft>` → 歧义非空则阻塞澄清 → 用户确认 → 编译为不可变 `TaskPolicy` + `policyVersion` |
| 达成指标 | 解析正确率 ≥90%（人工核对 ≥10 条典型输入）；四类样例（合法/可猜歧义/必须澄清/必须拒绝）分流正确 |
| 依赖决策 | ADR-002（结构化输出稳定性已验证） |
| 状态 | 🟡 → `FR-TASK-01` / `R1` |

**为什么规则先行**：`总则-4` 要求"必须澄清"与"必须拒绝"两类都能正确分流，而模型倾向"合理推测后继续"。
规则命中即可复现，LLM 只补空白。

`TaskDraft` 字段见 `10-器官-任务与规划.md` §1.1；`IntentExtractor` 必须可注入（规则/LLM/录制回放三种实现），
否则解析逻辑无法离线单测。

### 3.1.1 TaskPolicy 的可变边界

"不可变"不能一刀切。授权项不可变，**范围可以追加**——两者混同会把唯一合法的扩张路径一起堵死。

| 字段 | 可变性 | 说明 |
| --- | --- | --- |
| `targets` | ❌ 不可变 | 缩减可随时做，扩大必须走 `scopeAmendment` |
| `allowedTools` | ❌ 不可变 | 只随能力授予变（`05` §5.2） |
| `budget` | ❌ 不可变 | 追加预算视为新任务（否则两本账口径失效） |
| `timeWindow` | ❌ 不可变 | `{start, end}`，过期即停，拒绝码 `OUT_OF_WINDOW`（`05` §5.1 第 5 步） |
| `scopeAmendment` | ⚠️ 只增不减，**每次需一次新确认** | 发现关联资产时追加，不重建任务 |

**为什么必须有 `scopeAmendment`**：真实渗透里扫出子域名、发现关联 IP 是常态，不是越界。
`SEC-AUTHZ-01` 禁的是"**自行**扩展"，不是"扩展"。原设计"policy 不可变 + 只能 revoke 重建"
把用户主动追加这条路也堵了，代价是前面几十步的证据链全断、runId 换新、报告断成两半。

实现：`/pentest-scope add <target>` → 生成新 `policyVersion`（旧版留档）→ 一次人工确认 →
**同一 runId 继续**。审计落 `policy_amended`，带 `old` / `new` / `confirmedBy` / `stepId`。
`scopeAmendment` 只增不减：删目标要新建任务，因为删了没法证明"那段证据是在授权内取的"。

**谁能发起（必须写死，否则模型要么永远不敢提，要么自己先扫）**：

| 发起方 | 方式 | 生效条件 |
| --- | --- | --- |
| 用户 | `/pentest-scope add <target>` | 一次确认后生效 |
| **模型** | 只能经 `ask_user` 提"发现关联资产 X，建议追加授权" | 用户确认后生效；**不得先探一步再报** |
| 程序 | 不主动发起 | — |

模型从响应头、跳转、证书里看到关联域名时，正确动作是**停下并询问**。
先探一寸就已经构成越界访问——事后在报告里写"这是新发现的资产"，洗不掉已经发生的未授权交互。
这条比"发现能力"重要：宁可漏一个关联资产，不要多一次越界。

## 3.2 任务状态机

| 段 | 内容 |
| --- | --- |
| 实现手段 | 七状态 + 转移表（下表）；非法转移写 `task_transition_rejected` 事件、保持原状态 |
| 达成指标 | 42 组合（7 状态 × 6 事件）穷举，合法/非法各自断言；`STOPPED` 后任何输入不改状态 |
| 状态 | 🟡 → `FR-TASK-02` / `P1` |

| 当前 | 事件 | 下一状态 | 副作用 |
| --- | --- | --- | --- |
| `PLANNED` | `user_confirmed` | `AUTHORIZED` | 落 policy、开 runId |
| `PLANNED` | `user_rejected` | `STOPPED(revoked)` | — |
| `AUTHORIZED` | `first_action` | `RUNNING` | 首次调用放行 |
| `RUNNING` | `pause` | `PAUSED` | 冻结调度，保留状态 |
| `PAUSED` | `resume` | `RUNNING` | 从快照续跑，`pending` 标 `UNKNOWN_OUTCOME` |
| `RUNNING`/`PAUSED` | `stop(reason)` | `STOPPED` | 写终态事件 |
| `STOPPED` | 任何 | — | 拒绝，记 `code=STOPPED` |

**`PAUSED` 是本期新增**，需同步修订 `FR-TASK-03`（`1需求文档.md`）。

**收尾不新增状态**（保持 7 状态 × 6 事件 = 42 组合不变）：落终态事件**之前**必须过三项复核，
任一未过则 `stopReason=cleanup_incomplete`，报告标红且不得判"完成"：

1. 临时文件 / 生成脚本 / 临时凭据已清（**列清单，不假设**）；
2. 无仍在运行的子进程或监听端口；
3. 证据包已封（manifest 已写、`counts` 与目录一致）。

**清理动作同样走能力与预算判定**（`05` §5.1）——不能因为进入收尾就默认允许删除。
真实项目里最常出事的不是扫描阶段，是收尾阶段顺手 `rm` 掉不该删的东西。

## 3.3 计划与假设

| 段 | 内容 |
| --- | --- |
| 实现手段 | `Hypothesis` 为主数据；`suggestNext(state)→PlanHint` 产**建议**（阶段/允许类别/排序/阻塞原因），不产工具名与参数 |
| 达成指标 | 每次计划变更产 `PlanChangeEvent` 且 `trigger` 非空；R3 两案例可构造 |
| 状态 | 🟡 → `FR-AGENT-02` / `P2` |

**`suggestNext` 的输出边界**（与"两个 planner"的界线）：

| 允许输出 | 禁止输出 |
| --- | --- |
| 当前阶段、本阶段允许的工具类别 | 具体工具名 |
| **候选假设集合（无序）**、可重开的假设清单 | **排序建议**、调用序列 |
| 阻塞原因（无 spec / 达重试上限 / reopen 已用尽） | 工具参数（path/header/body） |

**为什么不再给"排序"**：排序就是策略——把 A 排在 B 前，等于定了先打谁。程序若给排序，
要么写死规则（僵化到无法应对真实目标），要么把策略藏在"软提示"里（比明说更糟，因为它不可审查）。
排序归模型，`suggestNext` 只负责把**候选集与约束**摆出来。
这不损害可复现性：可复现的是"同一状态给出同一候选集"，不是"同一状态做同一选择"。
后者本来就不该成立，否则 R3 的"动态调整"无从谈起。

数据结构见 `10-器官-任务与规划.md` §1.2。`PlanChangeEvent.trigger` 必填
`{stepId, factKey?, verdict?}`——**没有 trigger 的变更标 `untraced`，不计入 R3 证据**。

### 3.3.1 假设重开（`reopen`）

模型对一条已判 `inconclusive` 的假设，可发起**一次**重开。`INCONCLUSIVE` 有时意味着
"证据不够但方向对"，若全由程序判闭环，系统会提前收工，而模型连"我想再试一次"都说不出口。

| 项 | 规则 |
| --- | --- |
| 次数 | **每假设 1 次**，用尽不可再开 |
| 必填 | `reason`；缺理由的重开视为无效，内核拒绝并落 `hypothesis_rejected` |
| 代价 | 占一次预算（explore 或 verify，按工具类别） |
| 限制 | 重开后**必须换参**，同参被 I3 拦（`05` §5.4） |
| 审计 | 落 `hypothesis` 事件，`op=reopen`，带 `id` / `reason` / `stepId` |
| 与达成判据 | 存在 `reopen` 后仍未闭环的假设时，`objective_met` 不成立（`04` §4.6） |

**给一次就够**：给两次以上等于把"闭环"变成可以无限拖延的状态，`objective_met` 就永远判不出来。

## 3.4 三层记忆

| 段 | 内容 |
| --- | --- |
| 实现手段 | L0 台账（`Fact[]`）/ L1 工作记忆（渲染文本，≤1200 token）/ L2 归档（落盘，按 `observationRef` 取） |
| 达成指标 | L1 只由 L0 派生（`renderMemory` 纯函数）；超限按固定顺序裁剪并落 `memory_pruned` 事件 |
| 依赖决策 | 实测 Q3（`details` 是否入上下文）决定分层落点 |
| 状态 | 🟡 → `FR-AGENT-01` / `P3` |

**裁剪顺序（确定性）**：已闭环假设的历史 → 超过 5 步的旧 summary → 按事实类型（`path` 先丢，`port`/`cve` 最后）。
裁剪**不改事实集合**，只影响可见性。

**两条铁律**：不得维护第二份"记忆文本"；记忆必须可追溯到 `Fact key`（否则模型看到的和台账对不上，无法审计）。

| 段 | 内容 |

| 实现手段 | S0 角色与铁律（≤400 token，任务开始一次）+ S1 阶段行为（≤250 token，阶段切换一次） |
