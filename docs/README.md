## 1. 这个项目是什么

**一句话**：基于 pi-coding-agent 框架与 DeepSeek 驱动模型，面向**授权虚拟靶场**，构建一个**边界明确、可重复、可审计**的智能渗透测试辅助系统——工程化落地，非学术对比研究。

**目标用户**：校内安全方向学生——懂网络原理与漏洞理论，但"知道有 nmap，不知道此刻该对什么目标用什么参数"。Agent 补的是"工具翻译层"和"证据整理层"。

**目标（G1–G6）**：

| 目标 | 内容 | 状态 |
| --- | --- | --- |
| G1 | **自主探测与验证**：只给目标也能完成信息收集与漏洞验证，不依赖人给 CVE | 进行中 |
| G2 | 动态闭环执行（无效调用率 ≤ 30%，按自主性等级分账） | 进行中 |
| G3 | 受控执行边界（授权/工具/参数/预算/停止） | 控制层已实测 |
| G4 | 证据驱动报告（四态结论 + 效率事实字段） | 进行中 |
| G5 | 架构可演进（安全层框架无关） | ✅ spike 已验证 |
| G6 | **未知环境下的诚实性**：认不出、没手段、失败了都如实标注，不编造结论 | 待验证（P14） |

**不做什么**：未知漏洞自动挖掘、任意互联网目标、真实第三方系统、全自动 CVE 提交、企业级平台。

**核心闭环**：自然语言下达任务 → 解析为结构化配置 → 用户确认 → 信息收集 → 分析规划 → 受控工具调用 → 结果观察 → 动态调整 → 结论 → 报告，全程审计，危险操作人工确认。

> 这是**用户视角的使用流程**，不是 agent 的固定工作流：「分析规划」与「动态调整」由 agent 自主完成，
> 系统只约束调用边界与证据完整性，不预设步骤序列（见 `2规格/03` §3.3、`2规格/05` §5.2）。

**一条铁律**：实测表明候选模型对恶意渗透请求的越界服从率高达 90–100% 且加授权声明不降反升——**安全边界不能依赖模型自觉，必须由控制层强制拦截**（依据：`research/模型选型实验结果.md` §4 结论 2）。

**代码主体**：`src/pi-pentest/`（pi extension：安全控制层 + 工具层，2026-10-19 自 spike 迁入，240 项单测在本仓通过）。

### 编号怎么认

文档里字母多，**按长相认，别按字母认**：

| 长相 | 属于 | 例子 |
| --- | --- | --- |
| `FR-` / `SEC-` / `NFR-` / `FR-MODEL-` | 需求条目（做什么） | FR-AGENT-02 |
| `RA-N.x` | 工作包（一次可独立提交） | RA-1.3 |
| `R` + 数字 / `P` + 数字 | 场景验收（原有 / 新增） | R3、P14 |
| `C` + 两位数字 | 约束条目（性质级要求） | C13 |
| `T` + 一位数字 | 任务自主性等级（人给多少信息） | T1 人给 CVE / T3 存在未覆盖 |
| `U` + 一位数字 | 未知情形用例（P14 的四道题） | U2 有 CVE 无 probe spec |
| 最小档 / 折中档 / 全量档 | 实施范围（本期做多少包） | 折中档 17 包 |
| 字母 + 数字，只出现在设计文档 | 难点编号（哪里难） | B1 状态全内存 |

完整定义（状态标记、图示符号、六张总图、易误解术语）见 `design/agent-refactor/07-图例与编号约定.md` §1。
范围档与自主性等级**不使用 `A`/`B`/`C` 字母**，避免与难点编号混淆；早期文档的「A/B/C 档」= 最小/折中/全量档。

## 3. 四条主线怎么读

需求 → 规格 → 验收是一条**追踪链**（Requirement → Scenario → 可观察结果 → 验证方式 → Task），ADR 与 research 是支撑证据，路线图是推进节奏：

1. **需求（1）** 写"做什么"，长期稳定；
2. **规格（2）** 写"用什么技术手段达成指标"，随选型更新，未定的一律标"待定"指向 ADR；
3. **验收（3）** 只依赖需求的那层可早写；规格验收与模块级验收等对应 ADR 关闭后回填，不虚构；
4. **ADR** 一经决定不改写，决策变了新开 DCR。

## 4. 写作规则（改动本文档库前必读）

1. **单一事实来源**：同一事实只在一个文件里维护，别处用引用 + 文档内锚点。
2. **ID 稳定**：需求号（FR-*/SEC-*/NFR-*）、验收号（R*）、ADR 号一经发出不改写，废弃则标 DEPRECATED。
3. **追踪链**：需求 → 场景 → 可观察结果 → 验证方式 → Task，任何一层变更必须同步检查上下游。
4. **同步对抗组**：新文档或重大改动写完后，把变更摘要发给对抗组，让对方知道我方工作状态。
5. **需求与规格分离**：需求写"做什么"，规格写"用什么技术手段达成"，规格里未定的一律标"待定"指向 ADR，不预填结论。
6. **验收与选型同节奏**：选型未定之前不虚构验收内容；数值一律"首次试跑后冻结"。
7. **计划唯一入口**：计划类更新只写 `4工作项与路线图.md`；周志只记已完成的变更。
8. **周志与报告分离**：`weeklyLog/` 只写变更条目 + 验收结果 + 统计；实测证据、原始日志、复现步骤一律落 `verify/`，周志只留链接。
