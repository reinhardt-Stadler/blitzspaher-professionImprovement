# 2026-W48 · R4 三轮修复与 R1③ 语料

> 承接 [`2026-W48-R1R5验收.md`](2026-W48-R1R5验收.md)。那份记"跑出 0/6"，这份记"为什么"和修到哪。
> 详细数据见 [`../verify/2026-11-25-R4召回率.md`](../verify/2026-11-25-R4召回率.md)。

## 1. R1③ 语料：10/10

10 条不同表述（端口范围 / 具体端口 / 带协议 / 只给主机 / 带 CVE / 问句），
判据只看"首个调用的 target 是否含正确 IP 与端口"：

全部 PASS，**100%**（要求 ≥90%）。

**顺带暴露一件事**：`PENTEST_MAX_CALLS=4` 下多条结论是"无法验证"。
解析没错，是预算不够做完验证。**解析正确率与任务完成率是两件事**——
R4 的 0/6 属于后者。

## 2. R4 的三层根因（逐层修）

### 第一层：知识库检索静默截断（已修）

`knowledge_query {component:"struts2"}` 命中 20 条，但 `limit` 默认 10 且命中够数就 `break`。
CVE-2020-17530 排在第 10 条之后，agent 根本没看到，转去猜 S2-059。

修：`query()` 返回 `{ hits, total }`、默认 limit 30、summary 明说"共 N 条，显示前 M 条"。

### 第二层：查知识库被算作"无新证据"（已修）

修完第一层重跑，agent 连查三次 `knowledge_query`，`noNewEvidenceStreak` 直接到 3
（阈值 3），**内核在 `cve_check` 之前收了任务**。

知识查询本就不产 host/port 事实（总则-3 的 X2 已承认），拿"没新增事实"数它，
等于把查资料判成停滞。修：`producesFacts=false` 的工具既不累加也不清零 streak。

### 第三层：没有验证手段（未修，需决策）

第三层重跑 9m39s、12 次调用跑满，agent 终于读到 `struts2__s2-061`，
然后卡在这三条——它自己总结的，逐条都对：

1. 内置验证器只覆盖 3 个 CVE，知识库里 struts2 有 20 条
2. `toolgen` 未授予，`probe_forge` 被安全层拦下（它想自己写验证器但没权限）
3. 信息收集账 8/8 用尽，`http_probe` 被阻断

**知道该验哪条了，但没有验证手段。** 三个选项按代价排：加内置验证器 / 默认授予 toolgen /
放宽信息收集账配额。

## 3. 过程中的判断修正

第一、二层都是"修完一层才发现下一层"，而且每层单独看都像"模型不够聪明"。
只有把审计逐条摊开（调用序列 + newFactCount + streak），才看得出是机制在挡路。

这也说明**R4 这种全量验收不能靠单靶结论推断**：单靶跑一次看到 0 项，
很容易归因为"模型能力不足"；六靶 + 三轮修复才定位到三条具体的机制问题。
