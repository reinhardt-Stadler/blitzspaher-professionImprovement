## 5.3 RA-5.1 控制器（2026-11-15）

[`deploy/labs/lab.sh`](../../deploy/labs/lab.sh) + `labs.txt`，10 个候选靶（区间要求 6–8，多留余地按实际筛选）。

两个设计决定：

1. **一次只起一个靶**。Vulhub 的 Java 靶绝大多数钉死 8080，八个一起起必然冲突；
   起新靶时先停其它 `bz-lab-*` 并在输出里说明原因。
2. **端口以 `docker ps` 为准**，不以 [`labs.txt`](../../deploy/labs/labs.txt) 为准。compose 是端口映射的权威，
   两者不一致时用实际值并打 NOTE——否则会去探一个没人监听的端口，然后误判"靶场没起来"。

`reset` 用 `down -v` 再 `up`，不是 `restart`：被利用过的靶会留状态（上传的 webshell、
改过的配置），只 restart 会让第 N+1 次从与第 N 次不同的世界起步，轨迹不可比。

**当前状态**：控制器就绪，**靶场尚未实际起过**。`list` 已用假 vulhub 目录验过
（解析 / present 统计 / 不足 6 个的告警三个分支都正确），`start`/`reset` 需在 WSL 内实跑。

## 5.4 lab.sh verify：用 stub 跑出两个真 bug（2026-11-15）

把"起靶场"这件事收敛成一条命令后，用 stub docker + 假 vulhub 跑全流程（不必等真 docker），
跑出两个 bug。两个都不是测试环境问题，真 docker 上同样会犯。

### bug 1：`grep -E '->'` 的模式被当成选项

```bash
hit=$(printf '%s' "$ports" | tr ',' '\n' | grep -E '->' | head -1)   # 永远空
```

`->` 以 `-` 开头，grep 把它当选项解析，匹配不中任何行，且**不报错**。
后果链条：`hit` 空 → 端口取不到 → `http_ready ""` 返回假 → 每个靶都显示
`up=no port=?` → verify 报"0 个可重置"。

**危害不在于算错，而在于它会让人以为靶场全坏了**。真实 docker 启动正常、
容器健康、端口也在监听，脚本却一篇 FAIL，人会去查镜像、查网络、查 Docker 服务，
而真正的问题是一个少了 `-e` 的 grep。

修法：`grep -E -e '->'`。

### bug 2：选靶第二阶段只遍历了 `verifier=yes`

取样规则是"先取 2 个非硬编码，再从全池补齐"。但第二阶段写成了只遍历 `rest`
（即 `verifier=yes` 那组），于是非硬编码里第 3 个及以后的靶被永久丢弃：
6 个可用靶只选出 5 个，`want=6` 静默落空。

修法：第二阶段遍历 `pool`（全池）并用 `grep -qF "$name|"` 跳过已选。

### 顺带修的两处

- `sudo` 测试桩漏了 `shift`（把 "docker" 当子命令传进去），纯脚手架问题
- 失败时补 `hint: bash deploy/labs/lab.sh start <name>` —— 原先 `>/dev/null 2>&1`
  把失败原因全吞了，排查时无从下手
