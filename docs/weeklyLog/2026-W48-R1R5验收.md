## 2. R3 不成立是本轮最重要的发现

判据要求 `plan` 事件带 `trigger.stepId`。三次运行的事件类型分布：

```
decision 10 / 9 / 9，execution 9 / 9 / 9，capability_gap 3 / 0 / 1，run_end 各 1
```

**零 `plan`，零 `hypothesis`。** 而 `index.ts:238` 的 `mirrorToAudit` 已写好、`feed()` 会调它——
审计侧接线在，但 `ev.type === "plan_change"` 从未触发。

也就是说：**计划层没有进入实际 agent 循环**。不是 agent 没做动态调整，是内核的假设/计划
从未被激活。854 项单测全绿也测不到这一点，因为单测测的是内核逻辑本身，不测"它有没有被喂"。

**这一条不修，R3 与 MVP-1 的通过条件②永久不成立。**

## 3. 854 项单测全绿，真跑一次暴露 5 个缺陷

| # | 位置 | 缺陷 | 后果 |
| --- | --- | --- | --- |
| 1 | `reconstruct.ts` CLI | 只给 jsonl 路径时 `auditDir` 回落默认目录 | observation 全找不到 → `TRACE_MISSING`，**正确运行被读成没留痕** |
| 2 | `evidence.ts` | 无"能力缺失/不产事实"豁免 | 库缺失、自检、知识检索全算无效，无效率虚高（55.6%） |
| 3 | `evidence.ts` `extractFacts` | 对**所有**工具取 `evidence.url` 的 host | 查 NVD 时把 `services.nvd.nist.gov` 记成**目标 host**，台账被污染 |
| 4 | `evidence-collector.ts` | tar 用绝对 Windows 路径 + `-C` | GNU tar 把盘符当远程主机，**证据包永远产不出** |
| 5 | `tools.ts` knowledge 类 | 缺 `producesFacts:false` | 正确的知识查询被判"无新增事实" |

#2/#5 引入 X1（能力缺失，每工具豁免一次）与 X2（不产事实，每次豁免，靠 I3 抓重复）两类豁免。
豁免不进分母但**单列 excludedCalls**，不靠"消失"来让数字好看。

#3 是语义级：事实台账必须只记"目标观测"，情报源域名混进去会让命中率虚高、
报告的"触达目标"出现从未授权的地址。

#4 的根治不是加 `--force-local`，是**不给 tar 误判的机会**：cwd 设 outDir、全传相对名。

## 4. 两个环境限制（不是 bug，但要写下来）

1. **项目路径含单引号**（`Reinhardt's_ITmessage`）：Windows 侧走 `wsl.exe` 转交时，
   引号会被 Linux 端 shell 吃掉，`-v` 挂载直接失败。`toolhost` 的真容器验收在该路径下
   无法执行，已改为明确 SKIP。真跑要放到无引号路径（`npm run verify:toolhost`）。
2. **透明代理接管 TCP**：`192.0.2.1`（RFC 5737 保留段）被判 `open`，说明 clash TUN
   会替一切 TCP 建连。此时 `env_selfcheck` 的 timeout/refused 区分在物理上不成立，
   `selfcheck` 那条断言改为 SKIP 并输出告警。

第 2 条影响面比它看起来大：**在代理环境下，agent 会把"被代理接管"误读成"端口开着"**。

## 5.5 R3 已修（2026-11-25 当天）

按上面的顺序做了第 1 项。

**根因**：宿主只 feed `tool_call_started` / `tool_result` / `policy_confirmed` / `user_command`，
**从不喂 `hypothesis_proposed`**。而 `plan_change` 由它产生，于是整条假设/计划链路在真实
循环里是死的——不是模型不会调整，是内核从没被告知"你在验证什么"。

**修复两处**：

1. `KernelInput.hypothesis_proposed` 加 `stepId`，内核用它填 `trigger.stepId`。
   原本写死 `null` 并标 `untraced`，而 R3 判据明确要求 trigger 指向真实 step。
2. 宿主在 `tool_call_started` 前建模假设：用已积累事实作 basis（内核拒空 basis），
   再把调用关联到 `hypothesisId`。

**实测两靶对比**（T2，只给目标不给 CVE）：

| | A 靶 shiro 8080 | B 靶 fastjson 8090 |
| --- | --- | --- |
| 结论 | 0 项 + 正确上报验证器缺口 | **CONFIRMED fastjson** |
| 假设 basis | `path:/:302` | `path:/:200` |
| plan 变更 | 10 个 | 8 个 |

R3 四条判据形式上全过（plan 存在 / trigger 非空 / diff 不同 / 差异前事实不同）。

**但要诚实说**：两靶假设的 `statement` 是同一个文本（`探测 127.0.0.1（nmap_scan）`），
因为建模在首次调用、那时还没有 service 事实。diff 的差异主要来自执行步数，不是计划内容。
另外 10 个 plan 更新里 9 个 reason 都是"已识别组件但无可用验证手段"——那是
`onNoProbeSpec` 的缺口上报，**plan 事件变成了缺口日志**。

改进方向（未做）：发现新组件时建新假设，让 statement 反映"发现的是什么"，
两靶的假设内容才会真正分叉。

## 5.6 R3 弱点修补 + R4 全量（2026-11-25 当天）

### R3 两个弱点都补了

1. **假设 statement 带组件**：`service`/`version` 事实出现时另起一条假设。
   实测两靶终于分叉：A `探测 http://127.0.0.1:8080/（http_probe）`
   vs B `探测 172.27.194.209（nmap_scan）`。
2. **no_capability 只报一次**：原本每次调用都产 plan_change，10 条更新里 9 条是同一句
   "已识别组件但无可用验证手段"——plan 事件被缺口日志淹没。现在 A 靶只剩 2 条 plan
   （add + 1 次 update），B 靶同样。

R3 四条判据在 6 个 run 里全部成立（每个 run 都有 2–4 条 plan、1–2 条假设）。

### R4 全量：召回率 0/6

| 靶 | 预植 CVE | 实际 |

横向证据：有验证器覆盖的靶（fastjson）反而没调验证器，说明问题不在"有没有工具"，
在"知不知道该验哪个"。

## 5.7 模型会虚构内部机制（影响 R5③）

6 个 run 里**没有一次调用 `evidence_collector` 或 `pentest_report`**，但 agent 三次写出
"证据打包触发安全删除确认闸门，50/53/55 个暂存文件待确认"。

`SAFE_DELETE_BULK_CONFIRM_REQUIRED` 在代码与 pi 依赖里都不存在（已全库 grep）。
它虚构了一个内部机制来解释"我没有产出证据包"。

这种文字读起来完全像真的——只有对着审计才发现它没调过那个工具。
R5 要防的正是"把没做说成被拦住"，本轮它出现在自由文本里而不是结构化报告里，
但用户读的就是那段话。
