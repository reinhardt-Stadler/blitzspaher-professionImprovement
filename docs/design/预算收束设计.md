# 预算收束设计（SEC-BUDGET-01 实现方案）

> **对应**：SEC-BUDGET-01（执行预算）、SEC-STOP-01（停止机制）、FR-AGENT-05（报告生成）、OQ-09（数值冻结）
> **日期**：2026-11-07
> **状态**：设计稿（待实现）

---

## 0. 核心原则

> **预算不是"到点硬砍"，而是"有序收束"。**

硬停止的问题：任务跑到一半被砍，模型没有机会整理已有结论，
报告只剩半截，违反 G4「证据驱动报告」和 R5「四态结论」。

正确做法：**在预算耗尽前逐步提示模型收束**，让它主动整理并出报告。

---

## 1. 三档预算水位

```
100% ───────────────────────────────── 硬停止
  │
  │  【收束区】要求立即出报告，禁止新工具调用
  │
 90% ───────────────────────────────── 收束线
  │
  │  【告警区】提示预算紧张，建议聚焦已有线索
  │
 80% ───────────────────────────────── 告警线
  │
  │  【正常区】
  │
  0% ────────────────────────────────── 开始
```

| 水位 | 动作 | 对模型 | 对系统 |
|------|------|--------|--------|
| < 80% | 正常 | 无感知 | 只记录 |
| ≥ 80% | **告警** | 一次性提示"预算已用 80%，请聚焦已有线索" | 审计 `budget_warn` |
| ≥ 90% | **收束** | 一次性提示"预算接近上限，请立即汇总并生成报告，不要再发起新验证" | 审计 `budget_converge`；**阻断新工具调用** |
| ≥ 100% | **停止** | 不可再调用 | 审计 `stop: budget_exceeded`；强制收尾 |

### 为什么 90% 就阻断新调用

因为"再调一个工具"可能触发长推理（DeepSeek 单次 12K token），直接把预算打穿。
90% 就截断，留 10% 给模型写总结——**总结本身也要花 token**。

---

## 2. 预算维度

| 维度 | 阈值 | 说明 |
|------|------|------|
| **调用次数** | `maxCalls` | 已有实现 |
| **token 总量** | `maxTokens` | 新增；来自 pi `message_end` 的 `usage.totalTokens` |
| **运行时长** | `maxRuntimeMs` | 已有实现 |
| **成本（可选）** | `maxCostUsd` | pi 的 `usage.cost.total` 直接可用 |

> pi 的 usage 结构（实测）：
> `{ input, output, cacheRead, cacheWrite, reasoning, totalTokens, cost: { total } }`

**优先级**：任一维度达到水位即触发对应动作（取最严的那个）。

## 3. 实现方案

### 3.1 数据流

```
模型调用结束
    │
    ▼
pi: message_end (message.usage)
    │
    ▼
BudgetTracker.record(usage)      ← 累加 token / cost
    │
    ▼
BudgetTracker.level() → normal | warn | converge | exhausted
    │
    ├─ normal    → 什么都不做
    ├─ warn      → 一次性 sendUserMessage("预算 80%...")
    ├─ converge  → 一次性 sendUserMessage("请立即汇总出报告") + 标记 blockNewCalls
    └─ exhausted → control.halt("budget_exceeded")
```

### 3.2 组件

**新增 `src/pi-pentest/src/budget.ts`**（零 pi 依赖，可单测）：

```ts
export type BudgetLevel = "normal" | "warn" | "converge" | "exhausted";

export interface BudgetLimits {
  maxCalls?: number;
  maxTokens?: number;
  maxRuntimeMs?: number;
  maxCostUsd?: number;
  /** 水位阈值（默认 warn=0.8, converge=0.9） */
  warnAt?: number;
  convergeAt?: number;
}

export class BudgetTracker {
  recordUsage(u: { totalTokens: number; costUsd?: number }): void;
  level(): BudgetLevel;
  /** 某一维度的最大使用比例 */
  usage(): { calls: number; tokens: number; runtime: number; cost: number };
  /** 已发出过哪一级提示（防重复） */
  markNotified(level: "warn" | "converge"): boolean;  // 返回是否为首次
}
```

**`index.ts` 挂接**：
- `pi.on("message_end")` → 累加 usage
- `pi.on("tool_call")` → 若 level === converge/exhausted，`block` 新调用
- 首次进入 warn/converge → `pi.sendUserMessage(...)` 提示模型

### 3.3 提示词内容（关键）

**告警（80%）**：
```
[预算告警] 当前已使用预算的 80%（调用 8/10，token 96K/120K）。
请评估剩余线索的价值，优先处理最有把握的目标，避免低价值尝试。
```

**收束（90%）**：
```
[预算收束] 预算即将耗尽（token 108K/120K）。从现在起：
1. 不要再发起新的工具调用
2. 立即基于已有证据汇总结论
3. 调用 /pentest-report 生成报告
未完成的测试项会在报告中如实标为 NOT_EXECUTED。
```

**耗尽（100%）**：
```
[预算耗尽] 已停止调度。已采集的证据与结论仍可通过 /pentest-report 生成报告。
```

### 3.4 与安全控制层的关系

- **收束不是安全拦截**：它是资源管理，不改变 SEC-* 的裁决语义
- 但**耗尽时的 block** 走同一个 `tool_call` 漏斗，保持"单一入口"
- 审计事件新增：`budget_warn` / `budget_converge`（已有 `budget_warn`，扩展）

## 4. 报告中的体现

报告 §6「效率事实」需增加：

| 指标 | 说明 |
|------|------|
| token 消耗 | 输入 / 输出 / 推理 |
| 成本 | USD |
| 预算水位 | 结束时用了多少（如 92%） |
| 停止原因 | `budget_exceeded` / 正常完成 |
| 收束状态 | 是否触发了 warn / converge（说明报告的完整性受影响） |

> **诚实性**：若触发收束，报告必须声明"因预算收束提前结束，以下项目未完成"。
