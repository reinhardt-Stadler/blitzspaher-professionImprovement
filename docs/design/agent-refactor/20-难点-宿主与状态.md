# 20 · 难点：宿主边界（A1–A5）与状态外置（B1）

## A1 循环主权在 pi 手里 ⏸

**实质**：不止是"只能拿到 4 个钩子"。真正的问题是**审计语义**：如果记忆回注只能走 `steer`，
注入内容在会话里表现为"用户说的话"，那么"这个分支是模型看到前序 Observation 后自己选的"就成了不可证命题
——因为也可以解释成"用户提示了它"。

**已确定**：回注内容由内核纯函数生成（`renderMemory`）；注入文本可加固定标记；审计可落 `kind=inject` 独立事件。
**待定**：是否有专用注入钩子（OQ-14-1）。
**处置**：分支表见 `11-器官-记忆与知识.md` §1.3。补充一条：**无论哪个分支，R3 证据都必须来自
`plan` 事件的 `trigger.stepId`，不依赖对话记录**——这样即使走分支 B，证据链也不塌。

## A2 内置工具旁路 ⏸

**实质**：bash 的目标可藏在管道、变量、编码、子 shell 里。做 shell 文本解析来判"目标是否授权"，
本质上是写一个 shell 解析器并指望它没有洞——不可接受。

**已确定**：不做文本解析授权；一律 deny（ADR-006 第 1 条已决）。
**待定**：靠配置禁用还是靠漏斗 deny（OQ-14-2），以及最坏分支 C（`tool_call` 不覆盖内置工具）。
**处置**：三个分支见 `12-器官-状态建模与执行判定.md` §1.10。分支 C 需单列风险与替代方案（宿主级包装），不在此预设。

## A3 `hasUI` 为假时高危默认拒绝 ✅

**实质**：`index.ts:204` `if (!ctx.hasUI)` 直接 block。长任务基本一定在非交互环境跑，
这条等于"所有高危动作永远做不了"。

**已确定**：改为事前档位（`AuthorizationLevel`）+ 事中撤销 + 一次性提权申请。
`TaskPolicy` 增 `authorizationLevel`；`needsHuman` 语义从"每次弹窗"改为"档位不足时申请"。
**待定**：无——纯策略层改动，不依赖 pi 能力。
**处置**：与 B2 联动，档位进 policy 后 `configHash` 口径必须同步改。

## A4 `usage` 是 provider 私有字段 ⏸

**实质**：`index.ts:237` 从 `message_end` 的 `message.usage.totalTokens` / `usage.cost.total` 取数。
换 provider 或字段改名，token 记账静默归零——而"静默归零"会让预算永远显示健康，等于预算维度失效。

**已确定**：缺失即显式降级——写 `budget_degraded` 事件，`BudgetTracker` 标 `tokens: null`
（现有 `usage()` 已能把无限制维度算成 `null`），报告写"不可判定"，**不得写 0**。
**待定**：各 provider 字段形态（OQ-14-5）。
**处置**：`recordUsage` 增加"本次是否取到有效值"的返回，宿主据此写降级事件。

## A5 多 Agent 编排 🔴

**实质**：`OQ-12` 是演进项。但有个隐性约束：若内核 `reduce` 假设"单线程、单一状态"，
将来拆成执行 + 监察双角色就要重写。

**已确定**：本期**不做**，只在接口上留口——`reduce` 的输入输出都是纯数据，`KernelState` 可按 `taskId` 分片。
**处置**：RA-1 里只做"接口不妨碍未来"，不投工程量。**明确写"不做"，避免后期被当成欠账。**

## B1 状态全在内存，暂停恢复不成立 ✅（本期最大工程量）

**实质**：`control`/`budget`/`trace`/台账/未来的 plan 全是扩展加载时 `new` 出来的，进程一退全没。
而且不只是"存不下来"，还有**一致性**问题：`audit.jsonl` 已是 append-only 事件流，
状态另存一份，恢复后两者对不上怎么办。

**存储形态**：`state.jsonl`（append-only，权威）+ `snapshot-<seq>.json`（加速恢复）。

```jsonc
{"seq":7,"ts":"...","type":"task_transition","payload":{"from":"AUTHORIZED","to":"RUNNING"}}
{"seq":8,"ts":"...","type":"hypothesis_add","payload":{"id":"H-002","statement":"...","basis":["version:Jetty(9.4.z-SNAPSHOT)"]}}
{"seq":9,"ts":"...","type":"fact_ingested","payload":{"keys":["port:8090/tcp","service:8090:http"]}}
{"seq":10,"ts":"...","type":"verdict","payload":{"hypothesisId":"H-002","kind":"retry_change","reason":"inconclusive"}}
```

**恢复算法（五步，每步可单测）**

1. 取 `seq` 最大的 snapshot，载入 `KernelState`；
2. 重放 `state.jsonl` 中 `seq > snapshot.seq` 的行（每个 reducer 分支必须**幂等**，同 `seq` 重复应用不改变状态）；
3. 校验重放末 `seq` == 文件末 `seq`，不等 → `GAP_STATE_TRUNCATED`；
4. 与 `audit.jsonl` 的 `max(stateSeq)` 对账：state 领先 → `GAP_STATE_AHEAD_OF_AUDIT`（崩在两次写之间）；
   audit 领先 → `GAP_AUDIT_AHEAD_OF_STATE`（状态写失败但审计成功，更严重）；
5. `pending`（已发出未拿到 result 的调用）一律标 `UNKNOWN_OUTCOME`，**不重放**——
   工具可能有副作用，重放会制造第二次真实请求。

**快照策略**：每 20 个事件或阶段切换落一次；只保留最近 3 份。

**为什么不用 SQLite**：状态与审计会变成两条真相线，两写不一致要额外机制保证，
而"恢复点与 `audit.jsonl` 事件序对齐"这条硬要求用同一个 `seq` 最自然。
