## 1.1 目标与任务管理 ✅

**现状**：`index.ts:80` `buildPolicy()` 在扩展加载时执行一次，`taskId = task-<Date.now()>`，
`allowedTools` 硬编码三个，目标与预算全来自环境变量。无自然语言解析、无用户确认、无任务状态机；
`security-control.ts:141` 只有一个 `stopped` 布尔。`FR-TASK-02` 要求暂停，实际只有终止（`/pentest-revoke`）。

**目标**：自然语言 → 结构化草案 → 歧义显式暴露 → 用户确认 → 不可变 policy（带版本）→ 状态机驱动全流程，可暂停/恢复。

**实现**：三层分离，每层可单测。

```ts
// kernel/task/parse.ts —— 只产草案，不产 policy
export interface TaskDraft {
  targets: string[];                 // 归一化主机名（复用 extractTarget 的规则）
  requestedScope: string[];          // 原始范围表述，供用户核对
  toolCategories: ToolCategory[];    // 用户要做什么，不是工具名
  budgetIntent: { calls?: number; minutes?: number };
  suggestedLevel: AuthorizationLevel;
  ambiguities: Ambiguity[];          // 非空即必须澄清，禁止猜
}
export interface IntentExtractor {   // 可注入：规则实现 / LLM 实现 / 录制回放实现
  extract(text: string): Promise<Partial<TaskDraft>>;
}
```

- **混合解析策略**：先跑结构化规则（"对 X 做 Y"、显式 IP/CIDR/主机名、"预算 N 次"），命中字段直接采用；
  未命中字段才交 LLM，且 LLM 只能填 `Partial<TaskDraft>`，不能决定是否启动。
  理由：`总则-4` 要求"必须澄清 / 必须拒绝"两类都能正确分流，而模型倾向"合理推测后继续"，规则先行才可复现。
- **policy 不可变 + 版本链**：`policy-compiler.ts` 编译成 `TaskPolicy` + `policyVersion`；
  追加授权不改原对象，追加新版本并保留旧版（解决 B2）。
- **状态机**：`PAUSED` 为本期新增，需同步修订 `FR-TASK-03`。

| 当前 | 事件 | 下一状态 | 副作用 |
| --- | --- | --- | --- |
| `PLANNED` | `user_confirmed` | `AUTHORIZED` | 落 policy、开 runId |
| `PLANNED` | `user_rejected` | `STOPPED(revoked)` | — |
| `AUTHORIZED` | `first_action` | `RUNNING` | 首次调用放行 |
| `RUNNING` | `pause` | `PAUSED` | 冻结调度，保留状态 |
| `PAUSED` | `resume` | `RUNNING` | 从快照续跑，`pending` 标 `UNKNOWN_OUTCOME` |
| `RUNNING/PAUSED` | `stop(reason)` | `STOPPED` | 写终态事件 |
| `STOPPED` | 任何 | — | 拒绝，记 `code=STOPPED` |

非法转移**不抛异常**：写 `task_transition_rejected` 事件并保持原状态。长任务里抛异常等于让宿主决定语义。

**验收**：`R1` ①②③；`总则-4` 四类样例逐条分流正确，歧义样例**必须**停在 `PLANNED`。

## 1.2 规划与重规划 ✅

**现状**：`src/` 十个模块无任何 plan 结构。"下一步做什么"完全由模型即兴决定，
审计里只能看到"调了什么"，看不到"为什么是这一步"。

**目标**：显式、可序列化、可 diff 的假设清单；每步动作都能挂到假设上；重规划有明确触发条件。

**关键设计决定：假设是主数据，步骤是派生视图。**
反过来存步骤列表会立刻遇到两处不一致：改了假设但步骤没重排、删了步骤但假设还挂着。

```ts
// kernel/plan/types.ts
export interface Hypothesis {
  id: string;                        // H-001
  statement: string;                 // "8080 上的 Jetty 使用存在 CVE-2017-18349 的 fastjson 版本"
  basis: string[];                   // 支撑它的 Fact key（必须非空，否则是空想）
  probe: ProbeRef | null;            // null = 尚无验证手段 → status=unverifiable
  status: "open" | "supported" | "refuted" | "inconclusive" | "unverifiable";
  attempts: number;                  // 受 retry 上限约束（见 `12-…判定` §1.7）
  verdictLog: Array<{ stepId: number; conclusion: string; reason: string }>;
}
export interface Plan {
  version: number;
  phase: Phase;                      // P0..P4，由 phaseOf(facts) 派生，不手写
  hypotheses: Hypothesis[];
  allocation: { explore: number; verify: number };  // 两本账配额
}
```

- **`suggestNext(state)` 只产"建议"，不产"指令"**（见 `05-与pi分工与硬约束.md` §2）：

```ts
export interface PlanHint {
  phase: Phase;
  allowedCategories: ToolCategory[];        // 本阶段允许类别（供 gate 用，硬约束）
  openHypotheses: Array<{ id: string; statement: string; attempts: number }>;
  suggestedOrder: string[];                 // 假设处理顺序（软提示，不强制）
  blockedReasons: string[];                 // 如"无 probe spec""已达重试上限"
}
```

进入 L1 记忆文本，由模型决定"这一步调哪个工具、传什么参数"。**内核不输出工具名与参数。**
排序逻辑（纯函数）：`open` 且 `probe != null` 且 `attempts < maxRetry` 的，按
"证据强度 × 预期收益 / 预估成本"排；证据强度取 `basis.length` 与事实类型权重（`cve` > `version` > `service` > `port`）。

- **`plan_diff` 事件**是 R3 的直接证据形式：

```ts
export interface PlanChangeEvent {
  kind: "plan";
  op: "add" | "update" | "drop" | "reprioritize";
  hypothesisId: string;
  from?: unknown; to?: unknown;
  trigger: { stepId: number | null; factKey?: string; verdict?: string };  // 谁导致的
  reason: string;
}
```

`trigger` 是重点：R3 要证明"分支由前序 Observation 驱动"，必须能读到"哪条事实/哪次判定触发了变更"。
**没有 `trigger` 的 plan 变更一律视为无依据，不计入分支证据。**

- **重规划触发条件**（每条对应确定的**计划动作**——改假设状态/配额/工具健康，**不是**指派模型调工具）：

| 触发 | 条件 | 动作 |
| --- | --- | --- |
| 新事实与假设矛盾 | 假设声明 fastjson，`http_probe` 的 `Server` 却是 nginx | `refuted` + `drop`，从知识库重生成候选 |
| 探测无定论 | `INCONCLUSIVE` 且达重试上限 | `inconclusive`，报告如实标注，不再重发 |
| 无可用探测手段 | 有 CVE 但无 probe spec | `unverifiable`，进"未覆盖项" |
| 工具不可用 | 同一工具连续 2 次 I1 | `toolHealth=unavailable`，换工具/换目标 |
| 预算水位 | 进入 `converge` | 停止新增假设，只收束已有 |
| 用户注入 | `user_command` 或 steer | 重新解析意图，旧计划标 `superseded` |

**验收**：R3 两类分支案例必须可构造——
(1) `nmap_scan` 结果决定是否对 8080 做 `cve_check`（事实驱动选路）；
(2) `cve_check` 返 `INCONCLUSIVE` 后改参数回补而非重发（判定驱动改动作）。
两者都要在 trace 里看到 `plan` 事件带 `trigger.stepId`。
