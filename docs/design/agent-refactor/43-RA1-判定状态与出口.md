## RA-1.5 三态判定与停止收敛 ✅

判定表以 `2规格/04` §4.4 为准（**先看 `errorKind` 再看结论**，八行）。要点：

- `verdict()` 与 `assess()` **分开**，前者在内核（在线），后者留在 `evidence.ts`（离线）；
- `retry_change` 只给 `allowedVariations`（path / content_type / port），**不给具体参数**；照原参重发会被 I3 拦；
- `decideStop()` 收敛**七**个条件：预算耗尽 / 连续失败 / 重复 / 无新增证据 / 用户撤销 / 边界阻断 / **目标达成**。
  前六条是中止，第七条是完成，报告须分组呈现——没有第七条，正常跑完的任务只能报"无新增证据"，读起来像没查出东西；
- `target_unreachable` 不清 `toolHealth`；`parse_failed` 不重试（`2规格/06` §6.3.1）。

**验收**：八行逐行用例；`OBS-CASE-003` 四类异常落到不同分支；`retry_change` 缺 `allowedVariations` 时测试失败；
`errorKind=target_unreachable` 连续 2 次后 `toolHealth` 仍为 `degraded` 而非 `unavailable`。

## RA-1.6 状态外置与恢复 ✅（本阶段最重）

五步恢复算法见 `20-难点-宿主与状态.md` B1。要点：

| 事项 | 决定 |
| --- | --- |
| 权威源 | `state.jsonl`（append-only） |
| 加速 | `snapshot-<seq>.json`，每 20 事件或阶段切换落一次，留最近 3 份 |
| 幂等 | 每个 reducer 分支必须能重复应用同一 `seq` 而不改状态 |
| 对账 | 与 `audit.jsonl` 的 `max(stateSeq)` 双向比对，两个方向的缺口码不同 |
| `pending` | 恢复后标 `UNKNOWN_OUTCOME`，**不重放**（可能有副作用） |

**改动清单**：`kernel/persistence.ts`（读写+恢复+对账）、`security-control.ts`（`AuditEvent` 加 `stateSeq`）、
`reconstruct.ts`（识别两个新缺口码并让 `traceHealth` 降级）、`index.ts`（启动恢复、`agent_settled` 落快照）。

**验收（三条，缺一不可）**

1. **往返**：跑 10 步 → 落快照 → 杀进程 → 恢复 → 状态与杀前一致（深等，除 `pending`）。
2. **不重放**：杀在第 5 步已发出、未拿到结果的调用上 → 恢复后该调用为 `UNKNOWN_OUTCOME`，工具执行次数不增加（计数桩验证）。
3. **对账**：人为删掉一行 `state.jsonl` → 恢复时产 `GAP_STATE_TRUNCATED`，报告标 `TRACE_DEGRADED`。

## RA-1 出口条件

| 条件 | 判据 |
| --- | --- |
| 决定性 | 同一 `KernelState` + 同一 `KernelInput` 跑 100 次，输出哈希一致 |
| 零依赖 | AST 扫描：`kernel/` 无 pi / index / tools import |
| **不越界** | 五项全过（`05-与pi分工与硬约束.md` §3）：无模型调用、无对话历史、无轮次概念、无流式处理、`KernelAction` 无 `call_tool` |
| 可恢复 | RA-1.6 三条判据全过 |
| R3 可构造 | 两个分支案例各跑一次，trace 里 `plan` 事件带 `trigger.stepId` |
| 不停摆 | 现有 240 项单测仍全绿（内核是新增，不改旧逻辑） |

> **"不越界"的含义**：零依赖**不等于**自研 agent 框架。判断标准不是代码行数，而是
> "内核有没有开始决定调哪个工具、有没有开始管对话"。越过之后 pi 就只剩一个 HTTP 客户端，那才是真的白做。
