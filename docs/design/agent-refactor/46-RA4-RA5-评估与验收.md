**两个设计决定及其理由**：

1. **一次只起一个靶**。Vulhub 的 Java 靶绝大多数钉死 8080，同时起八个必然端口冲突。
   起新靶时脚本会先停掉其它 `bz-lab-*` 项目，并在输出里说明原因。
2. **端口以 `docker ps` 为准，不以 [`labs.txt`](../../../deploy/labs/labs.txt) 为准**。compose 文件才是端口映射的权威；
   两者不一致时脚本用实际值并打 NOTE，避免去探一个没人监听的端口。

**[`verify`](../../verify) 的取样规则**：先取 2 个 `verifier=no` 的靶（保证"至少 2 个需非硬编码 CVE"这条被真正测到），
再从全池补齐到 n 个。不先取这 2 个的话，样本可能全是内置验证器覆盖的靶，
跑出绿色也证明不了那条要求。

**[`verify`](../../verify) 的判定**：一个靶 PASS 必须**两次探测都通**——第一次证明能起来，
第二次（reset 之后）证明能回到可用的初始状态。只起得来回不去的靶，对重复运行毫无价值。

**重置语义**：`reset` 是 `down -v` 再 `up`，不是 `restart`。
被利用过的靶会留状态（上传的 webshell、改过的配置），只 restart 会让第 N+1 次运行
从与第 N 次不同的世界起步，轨迹不可比。



**阶段目标**：6–8 靶场重复跑，含动态工具与回连，对抗组按"只给目标"出题。
