## 1.3 领域行为定义 🟡（注入方式待 OQ-14-1）

**现状**：`index.ts` 全文只有 `registerTool` / `registerCommand` / 四个 `on` 事件，
**没有任何 system prompt 或角色注入**。渗透方法论完全靠模型即兴 + 用户 prompt 里的临时说明。

**实现**：分两层，内容现在就能写（不依赖注入方式）：

| 层 | 内容 | 预算 | 时机 |
| --- | --- | --- | --- |
| S0 角色与铁律 | 只做授权靶场；不得自行扩展目标；结论必须四态；无证据不得 `CONFIRMED` | ≤ 400 token | 任务开始一次 |
| S1 阶段行为 | 当前阶段（P0–P4）的允许动作、期望产出、禁止事项 | ≤ 250 token | 阶段切换时 |

- **不做**：把完整方法论写成两千字 prompt。两个理由：token 是硬约束；长 prompt 挤压 `max_tokens`，
  该模型 reasoning 吃配额严重（`2规格` §5 第 2 条已记录空输出成因）。
- **两种注入分支**：

| 分支 | 条件 | 做法 | 代价 |
| --- | --- | --- | --- |
| A | pi 有系统提示/上下文注入钩子 | 走钩子，与用户消息隔离 | 无 |
| B | 只有 `sendUserMessage(steer)` | 注入文本强制加 `[SYSTEM-INJECT:plan]` 前缀；审计落 `kind=inject` | 审计必须能区分"用户说的"与"系统注入"，否则 R3 无法证明"由 Observation 驱动" |

分支 B 不是死路：只要打标记 + 落审计，R3 证据仍成立（证据是审计事件，不是对话记录）。
**但实测结论出来前不得写进对外表述。**

## 1.4 记忆与上下文 ✅（上限待 OQ-14-3）

**现状**：`pipeline.ts:101` `end()` 把 Observation 落盘成 `observations/<run>/<id>.obs.json` + `artifacts/*.raw.txt`，
**但不回注**。模型每轮只看到 `content` 里的 `summary + JSON.stringify(evidence)`（`index.ts:138,155`）。
`EvidenceLedger`（`evidence.ts:99`）只在离线 `reconstruct` 里用，运行时不存在这个对象。

**实现**：三层记忆，只有 L1 进上下文。

| 层 | 内容 | 存放 | 进上下文 |
| --- | --- | --- | --- |
| L0 事实台账 | `Fact[]`（六类封闭枚举） | `KernelState.ledger` | 否（渲染成摘要后间接进） |
| L1 工作记忆 | plan 摘要 + 未闭环假设 + 最近 N 步 summary + 计数水位 | `KernelState` 派生 | **是**，硬上限 |
| L2 归档 | `observations/*.obs.json`、`artifacts/*.txt` | 磁盘 | 否，按 `observationRef` 单点回取 |

- **L1 渲染格式**：结构化短行，不是散文。

```text
[状态] P2 服务探测 | 调用 5/12 | token 62k/200k | 未闭环假设 2
[已知] host:target | port:8090/tcp | service:8090:http | version:Jetty(9.4.z-SNAPSHOT)
[计划] H-002 该 Jetty 内含 fastjson(CVE-2017-18349) → 待验证（probe 就绪，attempts 0）
[上一步] http_probe 200，Server 头返回 Jetty 指纹（obs=observations/run-x/a1.obs.json）
```

- **裁剪规则（确定性，不靠模型）**：总预算 ≤ 1200 token。超限按序丢：先丢已 `supported/refuted` 假设的历史、
  再丢超过 5 步的旧 summary、最后按事实类型丢（`path` 先丢，`port`/`cve` 最后）。裁剪动作写事件，
  便于事后解释"模型当时少看到了什么"。
- **两条铁律**：① L1 只能由 L0 派生（`renderMemory` 纯函数），不允许维护第二份"记忆文本"；
  ② 裁剪不改事实集合，只影响可见性。

**卡点（OQ-14-3）**：分层能否只在工具内部裁剪（`content` 放摘要、`details` 放全量）？
- `details` **不进**上下文 → 分层白捡，`content` 只放 `summary`；
- `details` **进**上下文 → `details` 必须缩成引用 id，全量只落盘。
  这会连带改 `index.ts:138/155` 与 `pipeline.asObservation`（现在依赖 `details` 里有 `evidence`/`summary`）。
  详细连带成本见 `30-扩展点-具体扩法.md` §3.2。

## 1.5 知识与假设生成 🟡

**现状**：`deploy/knowledge/generated/` 340 条 md + `index.json`（`entries:340, withCve:271, components:152`）；
`grep -rn knowledge src/` **零命中**；`tools.ts:485` 的 `CVE_PROBES` 只有 3 个探测器 + 6 个键。

**实现**：两个工具 + 一条生成路径。

```ts
knowledge_query(args: { component?: string; cve?: string; keyword?: string;
                        hasProbeSpec?: boolean; limit?: number }): Promise<{
  entries: Array<{ slug: string; component: string; cve: string | null;
                   title: string; hasProbeSpec: boolean; bytes: number }>;
  total: number; truncated: boolean;
}>;
knowledge_read(args: { slug: string; maxBytes?: number }): Promise<{   // 默认 8KB，硬上限 64KB
  title: string; body: string; truncated: boolean;
}>;
```

- 索引在容器内是 `/knowledge/index.json`（`KNOWLEDGE_DIR` 已由 compose 注入 `/knowledge`）。
  启动读一次进内存（124KB 可接受），正文按需读盘。
- **假设生成路径**（`kernel/knowledge/hypothesize.ts`，纯函数）：
  `component 事实` → `knowledge_query({component, hasProbeSpec:true})` → 候选 CVE（有 spec 的排前）
  → 每个候选生成一个 `Hypothesis`，`basis` 指向触发它的 `version`/`service` 事实。
- **必须守住**：检索结果只是**候选**，不是结论。`knowledge_query` 与 `cve_check` 是两个独立 step，
  报告不得把前者当证据；检索工具本身**不产生 `cve` 事实**。

**卡点**：探测规格化（C3，见 `22-难点-冲突与验证链.md`）决定 `hasProbeSpec` 覆盖率——RA-2 实测项，不预填数字。
另：`index.json` 的 `version` 字段**大量为 null**（抽样 coldfusion 两条均为 null），
**不能靠结构化字段做版本匹配**，只能读正文；全部为 null 与否需脚本统计（RA-2.2b）。

**验收**：新靶场接入**不改 `tools.ts`** 即可产生候选并完成至少 1 个非硬编码 CVE 的验证。
