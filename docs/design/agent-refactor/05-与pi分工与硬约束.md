# 05 · 与 pi 的分工，以及三条硬约束

> **位置**：决策层 · 回答"内核零依赖是不是等于自研 agent"
> 上游：`02-目标架构.md` 原则三　下游：`20-难点-宿主与状态.md`、`42-RA1-内核骨架与规划.md`
> 对应决策：ADR-001（pi 选型不变）、DCR-002（pi 角色收窄）、ADR-005（内核外置）

## 0. 先分清两种"基于框架"

"基于框架做扩展"有两种完全不同的关系，混在一起就会得出"内核外置＝把 pi 变成能力面"的结论。

| 维度 | **插件 in 宿主** | **应用 on 运行时** |
| --- | --- | --- |
| 典型例子 | VS Code 扩展、Obsidian 插件、Chrome 扩展 | React 应用跑在浏览器、Spring 应用跑在 Tomcat |
| 谁是产品 | 宿主是产品，插件是增值 | 应用是产品，运行时是底座 |
| 循环归谁 | 宿主 | 应用（至少语义归应用） |
| 状态归谁 | 宿主（插件不该持独立状态） | 应用 |
| 换掉宿主 | 插件作废，重写 | 只改适配层 |
| 本项目 | ✅ **接入方式**是这样 | ✅ **架构关系**必须是这样 |

**关键：接入方式与架构关系是两件事。** pi 只提供"插件式"的入口（`pi --extension`），
所以我们**看起来**像插件；但产品定位是"一个渗透 Agent"，不是"给 pi 加几个工具"，
所以**内部**必须是"应用 on 运行时"。两者不矛盾，只是容易混。

判断自己在哪种形状，一个问题就够：**把 pi 换掉，要改多少行？**
只改 `index.ts` → 应用 on 运行时；大部分要重写 → 插件；压根不用 pi → 自研。
这就是下面 §3 越界线与 `3验收/06` 的 C35 想锁住的东西。

**pi 没有被削弱，它是被正确定位。** 浏览器也是"能力面"——给你 DOM、事件、网络、渲染；
React 应用有自己的状态管理与数据层，但没人说这"把浏览器从完整整体降级成了能力面"。
运行时就该只做运行时的事。真正会削弱 pi 的，是第 1 节那张表里它该做的事被我们抢走。

## 1. 核心判断：循环归 pi，边界归内核

**零依赖的是"判断层"，不是"循环层"。** 内核里没有循环——没有 `while` 调模型、没有工具 dispatch、
没有流式处理、没有上下文窗口管理、没有会话历史。它只有一个 `reduce(state, input)`。

| pi 提供（已核实的 API） | 若砍掉 pi，要自己造 | 与课题的关系 |
| --- | --- | --- |
| agent loop（多轮工具调用、错误回灌、重试） | 一套可持续的 turn 管理 | 无。任何框架都有，属商品 |
| `defineTool` + TypeBox schema 校验（`index.ts:126`） | schema 校验 + 非法输出回灌 | 无 |
| 会话与消息历史、上下文窗口装配 | 会话存储 + 裁剪 + 压缩 | 无，且最容易做错 |
| `@earendil-works/pi-ai` 的 provider 适配与 `usage` | 多供应商客户端 + token 记账 | 无 |
| `ctx.ui.confirm` / `registerCommand` / `notify` | TUI 或 CLI 交互层 | 无 |
| 4 个钩子（`tool_call`/`tool_result`/`message_end`/`agent_settled`） | 自己定义扩展点 | **有：这是唯一挂接面** |

被砍掉的都是商品，保留下来的才是课题。产出是"边界怎么强制、证据怎么留、方向怎么固定"，
不是"多轮循环怎么写"。ADR-001 否决自研 Orchestrator、ADR-005 淘汰方案三，理由相同。

## 2. 双方各管什么

| 层 | 管什么 | 不管什么 |
| --- | --- | --- |
| pi agent loop | 这一步调哪个工具、传什么参数；会话与上下文窗口；schema 校验；流式与重试 | 不管边界、不管阶段、不管证据、不管何时该停 |
| 内核 | **阶段与边界**：现在 P 几、这个调用放不放行、预算剩多少、结论够不够、要不要停、状态怎么存 | 不选工具、不拼参数、不排调用顺序 |

内核给模型的是**约束与事实**（"你在 P2，只允许 web_probe 类；台账已有 8080/http；同参重发会被拦"），
不是**指令**（"下一步调 http_probe，path=/admin"）。前者是策略层，后者是自研框架。

接口上的体现：`KernelAction` 只有四类——`inject` / `ask_user` / `require_level` / `stop`，
**没有 `call_tool`**。接口定义见 `42-RA1-内核骨架与规划.md` RA-1.1。

## 3. 越界线（出现任意一条，说明内核开始重写 agent）

1. 内核里出现调用模型的代码（拼 `messages`、import model client）；
2. 内核里保存对话历史（内核只该有事实台账，不该有"模型说过什么"）；
3. 内核需要知道"这是第几轮对话"；
4. 内核需要处理流式 / 增量输出；
5. 内核自己 dispatch 工具执行，或产出带具体参数的调用指令。

前四条可用 import 扫描与类型检查断言，第五条用类型断言即可（联合类型里没那个分支，写错编译不过）。
这是 RA-1 出口条件之一。

## 4. 什么情况下应该真砍掉 pi

不设"永远别砍"这种教条。出现任意**两**条即重开 ADR-001，而不是继续打补丁：

1. 宿主适配层（`index.ts`）代码量持续超过内核本身——说明 pi 的抽象与我们的模型不匹配；
2. OQ-14 五项里 ≥3 项结论为"不支持"，且都影响核心能力（内置工具完全绕不过、无任何注入点、`usage` 取不到）；
3. pi 停维护或锁死版本（当前锁 1.2.0，`Dockerfile` 已固定）。

现在三条均不成立。**但第 1 条要盯着**：内核与适配层的代码量比例，是判断"有没有跑偏成框架"最直观的指标。

## 5. 三条跨主题硬约束

贯穿全部实现章节，写代码前先确认没违反：

1. **封闭枚举不动**：`host/port/service/version/path/cve` 不增不减。认知层用投影，不改枚举。
2. **四态不动**：`CONFIRMED / NOT_CONFIRMED / INCONCLUSIVE / NOT_EXECUTED` 不加第五态。
   回连这类更强证据作为**正交维度** `verificationLevel` 附在结论上——因为 `3验收文档` 总则-1 的
   `cve` 事实键里含四态字符串，加态等于让历史台账与统计口径同时失效。
   > 此条尚待确认：若坚持加第五态，要同步改验收总则-1、`report.ts` 的 `Conclusion`、`evidence.ts` 的键格式。
3. **审计事件单一事实来源**：`src/audit-schema.ts` 是唯一 schema 定义处，四个消费者只读它，不各自定义。
