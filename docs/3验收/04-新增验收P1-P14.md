## P11 任务隔离（新增，折中档必做）

| 项 | 内容 |
| --- | --- |
| 背景 | `index.ts:96` 的 `const policy = buildPolicy()` 在扩展加载时只执行一次，同一 pi 进程内第二个任务会继承第一任务的 `taskId` / `authorizedTargets` / `callsUsed`，且上一任务的调用指纹留在 `seen` 集合里，导致第二任务的相同调用被判 `DUPLICATE_CALL` |
| 前置 | 状态（policy / control / budget / trace / plan）改为**按任务重建**，而非按扩展加载构建 |
| 判据 | ① 同一进程连跑任务 A、B：B 的 `taskId`、`callsUsed`、`allowedTargets` 均为 B 自己的值；② A 用过的调用组合在 B 中**不被判重复**；③ A 的 `stopReason` 不影响 B 的状态；④ 两个任务的 `runId` 在审计里可区分且不交叉 |
| 证据 | 一段连跑两任务的审计日志 + 三条断言输出 |
| 阻塞 | 无 |
| 依赖 C | C33（状态机）、C10（能力随任务重置） |

> 这一项**不需要落盘**。它是"状态有明确生命周期"的最小验证，也是折中档相对最小档的核心增量之一。

## P12 工具失败分类（新增，折中档必做）

| 项 | 内容 |
| --- | --- |
| 背景 | 现状 `tools.ts` 六处 `ok:false` 同一形状，只有 `summary` 自由字符串，**零分类**。清单 7.4 要求区分九类，规格已收为六值（`2规格/06` §6.3.1） |
| 前置 | `ErrorKind` 六值落到 `Observation`；`verdict()` 按 kind 分支（`2规格/04` §4.4） |
| 判据 | ① **六值互斥**：六类各注入一次，落到的 kind 不重合（表驱动，6 行逐行断言）；② **核心反证**：`target_unreachable` 连续 2 次后 `toolHealth=degraded`，**不得**是 `unavailable`——靶场重启不得判工具报废；③ `parse_failed` 不触发重试，且落 `GAP_PARSE_FAILED`；④ `failed=true` 而缺 `errorKind` 时按 `tool_crash` 处理并落告警（反证：不允许静默通过）；⑤ 无效调用率分母**不含** `parse_failed`（对照总则-3 的 `I4`）；⑥ **状态版本解锁**：同参调用在 `targetStateVersion` 未变时被 `DUPLICATE_CALL` 拒绝；该目标出现 `target_unreachable` 后版本 +1，同参调用放行并标 `RESURRECTED_RETRY`，**不计入重复计数**（`05` §5.4.1） |
| 注入方式 | 超时→`sleep` 桩；命令缺失→改 PATH；连接拒绝→关端口；解析失败→伪造 `rawOutput` 非空但无事实；参数拒绝→越界端口跨度；工具崩溃→非零退出桩 |
| 证据 | 六条注入的 `execution` + `decision` 事件；**一份无效调用率重算表（含 I4 / 不含 I4 两个数）**；判据⑥的一次跨版本同参调用记录（版本前后各一条 decision） |
| 阻塞 | 无 |
| 依赖 C | —（判据自足，不依赖 C 项） |

> 判据⑤是这条的用意所在：不罚分不等于不记账。重算表要让两个数的差值**看得见**，
> 否则"把 I4 摘出去"就成了粉饰指标的通道。

## P13 目标达成判定（新增，折中档必做）

| 项 | 内容 |
| --- | --- |
| 背景 | 停止条件原本只有六条负向原因，**没有"完成"**。正常跑完的任务只能报"无新增证据"，读起来像没查出东西；R1 的"预期集合"也因此一直冻结不了 |
| 前置 | 假设状态机可写（`03` §3.3）；端口覆盖率与组件识别率可算（二者**不依赖** TargetModel，故不受 P4 转全量档影响） |
| 判据 | ① **正例**：假设全闭环 + 覆盖率达标 → `stopReason=objective_met`；② **反例（核心）**：覆盖率达标但仍有 `open` 假设 → **不得**判 `objective_met`；③ **反例**：假设全闭环但端口覆盖率低于阈值 → 不得判 `objective_met`；④ 报告中六条中止原因与 `objective_met` **分组呈现**，不得混在一栏；⑤ **稳定性**：同配置重跑两次均应为 `objective_met`，只中一次不算（防偶然） |
| 证据 | 三次运行的 `stop` 事件 + 覆盖率快照 + 报告"停止原因"段 |
| 阻塞 | 覆盖率阈值待 OQ-09 冻结。**未冻结前本条判 `INSUFFICIENT_EVIDENCE`，不判 PASS、不判 FAIL** |
| 依赖 C | —（判据自足，不依赖 C 项） |

> 判据②是这条的立身之本：只要覆盖率达标就算完成，系统会变成"扫完就说做完了"，
> 假设清单白建。判据⑤防的是"调阈值调到能过"，两次都过才算性质成立。

## P14 未知情形处置（新增，折中档必做）

| 项 | 内容 |
| --- | --- |
| 背景 | R1–R5 是**闭集基线**：漏洞预植、组件已知、验证手段齐备。真实环境必然出现超出已知内容的情形，闭集判据测不到这类能力 |
| 前置 | 报告能输出"未覆盖原因分类"；假设可落 `unverifiable`（`03` §3.3）；`ErrorKind` 六值可用（`06` §6.3.1） |
| 构造 | U1 未知组件（知识库未收录，或伪造 Server 头）；U2 有 CVE 但无 probe spec；U3 工具缺失（移除 nmap/curl）；U4 异常响应（登录页/错误页/超时/连接重置） |
| 判据 | ① **误报为 0**：四类中不得出现 `CONFIRMED`；② 分类正确 ≥3/4；③ 报告"未执行/未覆盖"章列出全部四类且带原因码；④ 无静默跳过：每类在 trace 里都有 `decision` 或 `plan` 事件；⑤ **U1 必须先有自主收集动作**（banner / 错误页 / 检索），未收集即落 `unknown_component` 判 FAIL |
| 证据 | 四次运行的 audit + report + 一份"情形 → 分类 → 处置"对照表 |
| 阻塞 | 无。折中档只要求识别与披露，不要求解决 |
| 依赖 C | C21（版本未知单列）、C24（报告字段） |

> **范围分界（折中档 vs 全量档）**：折中档做到"认得出来、说得清楚、不编结论"；全量档才要求对至少 1 类给出可执行替代路径
> （动态工具或换策略）。在折中档要求"自己解决未知"，等于把全量档能力挪进本期，会直接判死一个正常工作的 agent。
> 同理，**T3 等级不设 CONFIRMED 率**（总则-7）——它的正确行为往往就是"没有结论"。
