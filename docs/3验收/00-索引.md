# 验收 · 索引

> **定位**：验收回答"**怎么证明做到了、由谁判、判据是什么**"。
> 上位：`1需求文档.md`（要什么）、`2规格/00-索引.md`（怎么做）。
> 体量规矩：单文件 ≤200 行。

## 1. 两支结构

验收分两支，回答两类不同的问题：

| 支 | 回答 | 编号 | 判定方式 |
| --- | --- | --- | --- |
| 场景验收 | 这个任务跑完，结果对不对 | `R*` / `P*` | 跑靶场、看报告、看证据 |
| 约束验收 | 这个实现性质成不成立 | `C*` | 单测、静态扫描、类型断言、走查 |

两支交叉：一个 R/P 项依赖若干 C 项成立；一个 C 项可能被多个 R/P 项间接验证。
映射见 `06-约束条目.md`。

**为什么要两支**：有三类问题用场景验收根本答不了——
"内核是否真的零依赖""杀进程后会不会重放工具""图模型与台账是否一致"。
这些性质不成立时，R 项通过也是蒙对的。

## 3. 判定词汇

| 词 | 含义 | 禁止用法 |
| --- | --- | --- |
| `PASS` | 按判据判通过 | — |
| `FAIL` | 按判据判不通过 | — |
| `INSUFFICIENT_EVIDENCE` | 证据不够判 | **不得**当作 PASS 或"未发现问题" |
| `NOT_APPLICABLE` | 该场景不适用 | 单组实验的 A/B 列可填；环境哈希与证据位置不可空 |

数值类结论首次试跑后冻结，未实测不预填。**`0%` 与"不可判定"是两个不同结论**，
可判定数为 0 时必须写后者。

## 4. 编号规则

| 前缀 | 含义 | 例 |
| --- | --- | --- |
| `R*` | 原有场景验收（编号与判据冻结，不改） | R1、R7、R10 |
| `P*` | 新增场景验收 | P2 计划可审查、P11 任务隔离 |
| `C*` | 约束条目（性质级，任何实现都必须成立） | C13 全量白名单 |
| `EXT-DIFF-*` / `SEC-CASE-*` / `OBS-CASE-*` | 实验附录（沿用） | EXT-DIFF-001 |

新增能力一律进 P 或 C，**不动 R 的编号与判据**。

## 5. 执行顺序

```
① C 项（离线：单测 / 扫描 / 类型断言）   ← 每次提交都跑
        ↓ 全绿才有意义
② P 项（阶段出口：部分需真实运行）
        ↓
③ R 项（里程碑：需靶场与模型）
        ↓
④ 实验附录（A/B 对照与重复运行）
```

性质不成立时跑场景，只会得到一堆无法解释的失败。
