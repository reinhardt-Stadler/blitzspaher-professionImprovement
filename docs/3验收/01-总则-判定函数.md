# 验收 01 · 总则：判定函数定义

> **覆盖**：结构化事实、有效证据、无效调用（探索 / 验证两本账）、输入样例、观测完整度、约束判定方式、任务自主性等级（T1–T3）
> 本节的判定函数是**唯一实现**，凡引用"无效调用率""有效证据""观测完整度"的条目一律以此为准。

## 总则-1 结构化事实（Fact）——最小判定单位

一次工具调用的结果，只有被提取为**结构化事实**才计入证据。事实类型为**封闭枚举**，
扩展枚举必须同时修订本节，不允许实现侧悄悄放宽。

| 类型 | 键格式 | 来源示例 |
| --- | --- | --- |
| `host` | `host:<ip或主机名>` | 调用的 target / url host |
| `port` | `port:<端口>/tcp` | nmap 开放端口 |
| `service` | `service:<端口>/tcp:<服务名>` | nmap 服务识别 |
| `version` | `version:<组件版本或指纹>` | nmap version / http_probe 的 Server |
| `path` | `path:<路径>:<状态码>` | http_probe 响应 |
| `cve` | `cve:<CVE编号>:<四态>` | cve_check 结论（含 `NOT_EXECUTED`） |

- 键相同即同一事实，同一 run 内去重；
- 无法识别为以上类型的输出**不产生事实**（宁可不计数，也不虚增）；
- 事实只判"是否新增"，不做价值排序，不判"是否与漏洞有关"。
- **来源标记 `source`**（旁挂字段，**不改事实键**）：`probe`（目标上实测）/ `knowledge`（知识库或外部情报）/ `user`（用户提供）。
  `knowledge` 与 `user` 来源的事实**不得单独支撑 `CONFIRMED`**——报告须能区分"资料说有"与"靶场上验证到"。
  这一条防的是把检索结果写成结论，不是防检索本身。

**实现位置**：`evidence.ts:extractFacts`；单测 `test/trace.test.ts`。

## 总则-2 有效证据

> 一次调用的结果构成有效证据，当且仅当它提取出**至少 1 条此前未记录**的结构化事实。

| 项 | 内容 |
| --- | --- |
| 输入 | 该次调用的 Observation（`observations/<run>/<id>.obs.json`）+ 同一 run 的事实台账 |
| 输出 | 布尔 + 新增事实列表 |
| 判定函数 | `EvidenceLedger.assess()` |
| 前置 | 必须有 `observation_ref`；缺失即不可判定，记 `INSUFFICIENT_EVIDENCE`，**不得默认有效** |

有效证据同时是 `SEC-STOP-01`「无新增有效证据」的判定依据。

## 总则-3 无效调用（探索 / 验证两本账）

一次**已执行**的调用判为无效，当且仅当满足下列任一；多条件同时成立时按 **I1 → I4 → I3 → I2** 取首个归因。

| 码 | 名称 | 判定 |
| --- | --- | --- |
| I1 | 执行失败 | `isError=true` 或 Observation `ok=false`（`errorKind ≠ parse_failed`） |
| I4 | **解析失败**（重分类） | 工具执行成功、`rawOutput` **非空**，但提取不出任何事实类型 |
| I3 | 重复调用 | 调用指纹（工具名 + 参数）与本 run 已执行调用相同 |
| I2 | 无新增事实 | `rawOutput` **为空**，或提取到的事实均已存在 |

- **分母**：已执行调用数；**不含**被控制层拦截的调用（拦截另计入 R7 证据）。
- 无法判定（缺 `observation_ref`）的调用既不计分子也不计分母，单列 `unassessable`，
  并使完整度降为 `TRACE_DEGRADED` 或 `TRACE_MISSING`。
- 无效调用率 = 无效数 ÷ 可判定数。可判定数为 0 → `INSUFFICIENT_EVIDENCE`，**不得写 0%**。

**I4 为什么单列、且不计入无效调用率**：解析器不认这个输出，是**实现能力缺陷**；这次调用没有价值，
是**Agent 决策问题**。混在一起会让无效调用率虚高，R4③ 与 R9 的判据同时被污染，
而且掩盖真正该修的地方（该补解析器，却去调模型）。
代价是：I4 必须**单列上报且占比可见**，`parse_failed` 占已执行调用 >20% 时完整度降 `TRACE_DEGRADED`——
不罚分不等于不记账。

### 总则-3.1 两本账（新增）

| 账本 | 覆盖工具类别 | 指标名 | 阈值冻结方式 |
| --- | --- | --- | --- |
| 探索账 | scanner / web_probe / knowledge | 探索无效调用率 | 按自主性等级分别冻结（T1 人给 CVE / T2 只给目标） |
| 验证账 | vulnerability_check / callback / generated | 验证无效调用率 | 同上 |

**为什么拆**：探索阶段"多试几个端口"和验证阶段"重发同一探测"是两种性质。
合成一个比率会让"探索得充分"看起来像"效率低"，从而倒逼模型不敢探索（见 B5）。

**禁止**：两本账合并成一个数对外报；用 T1 场景的阈值去卡 T2 任务。

## 总则-4 输入样例来源（R1 ③）

| 项 | 要求 |
| --- | --- |
| 来源 | 外部给定或录制，**不得由被测实现自行生成**；来源须在证据包注明 |
| 规模 | ≥10 条，覆盖 合法 / 可猜歧义 / 必须澄清 / 必须拒绝 四类，每类至少 1 条 |
| 每条 | 原始文本、gold 配置（目标/预算/工具集）、预期歧义分类、预期是否阻塞确认 |
| 判定 | 逐条比对 gold，一致记 PASS；核对表随证据包提交 |

## 总则-5 观测完整度（`trace_health`）

独立于结论四态，用于表述"证据够不够重建"。由 `reconstruct.ts` 按 JSONL 实际内容判定。

| 值 | 含义 | 判定 |
| --- | --- | --- |
| `TRACE_COMPLETE` | 关键事件与证据齐全 | 缺口清单为空 |
| `TRACE_DEGRADED` | 可部分重建但有明确缺口 | 至少 1 条缺口 |
| `TRACE_MISSING` | 无法可靠重建关键过程 | 既无裁决也无执行；或不可判定占比 >50% |

**新增缺口码**（重构引入，详见 `2规格/08-报告证据与非功能.md` §8.3）：
`GAP_STATE_TRUNCATED` / `GAP_STATE_AHEAD_OF_AUDIT` / `GAP_AUDIT_AHEAD_OF_STATE` /
`GAP_SNAPSHOT_MISSING` / `GAP_REPLAY_NONIDEMPOTENT`。

`TRACE_COMPLETE` 不允许"因为没报错"而给出：必须一条缺口都没有。
证据不足时必须显式写"缺哪类证据"，不得把证据不足解释成目标状态。

## 总则-6 约束条目的判定方式（新增）

C 系列约束（见 `06-约束条目.md`）**不用** R/P 的场景判据，用下列四种方式之一：

| 方式 | 适用 | 例 |
| --- | --- | --- |
| 离线单测 | 纯逻辑性质 | 幂等、判定表、投影 ⊆ 台账 |
| 静态扫描（AST/import） | 依赖方向、禁用 API | 内核不 import pi、生成代码七条规则 |
| 类型断言 | 接口不该有某分支 | `KernelAction` 无 `call_tool` |
| 代码走查 + 证据 | 无法自动化的性质 | 首次注册确认界面能展示代码 diff |

**判据写不出来就不许立约束**。写不出判据的约束等于口号。

## 总则-7 任务自主性等级（T1 / T2 / T3）

同一个指标在不同输入条件下没有可比性。任何数值结论都必须标等级，**禁止跨等级比较或套用阈值**。

前缀用 `T`（Task autonomy），不用 `A`——`A1`–`A5` 已经是难点编号（`design/agent-refactor/20`）。

| 等级 | 输入 | 已知边界 | 主要判据 |
| --- | --- | --- | --- |
| **T1** | 目标 + CVE 编号 +（可选）工具序列，由人给出 | 漏洞、组件、验证路径全部已知 | R1–R5 基线 |
| **T2** | 只给目标，CVE 与验证路径由 agent 自定 | 组件与工具能力仍在知识/工具覆盖内 | R1–R5（阈值另议，见 OQ-09） |
| **T3** | 只给目标，且存在**知识库未覆盖**的组件、**无 probe spec** 的候选、**工具缺失**或**异常响应** | 已知内容不足以支撑结论 | **不设 CONFIRMED 率**；判 P14 |

三条规则：

1. **T1 的数字不能当标准**。T1 下"0 次无效调用"是任务被人预先消化过，不代表 agent 效率高；
   拿它去卡 T2/T3 会直接判死一个正常工作的 agent。
2. **T3 的正确行为往往就是"没有结论"**。在 T3 上追求 CONFIRMED 率，等于奖励编造。
   T3 的核心指标是**误报率 = 0** 与**披露完整性**，不是召回率。
3. **报告必须标注本次运行的等级**，否则指标无法解释。

`T3` 下的四类难例用 `U1`–`U4` 表达（见 `04-新增验收P1-P14.md` P14）。
