## 1. 功能验收

| ID | 验收项 | 前置条件 | 关键指标 | 证据形式 | 结对组 |
| --- | --- | --- | --- | --- | --- |
| R1 | 任务创建与状态流转 | 合法靶场可用 | ① 创建成功率 100%；② 状态流转与审计一致；③ 自然语言解析正确率 ≥90%（≥10 条，样例来源见总则-4） | 审计日志 + 状态截图 | ★ 复现 |
| R2 | 工具调用 | 注册表 ≥N 种（N 随工具定型冻结） | ① 调用 ≥N 种预注册工具；② 每次经控制层授权检查；③ 记录字段完整 | 审计日志 | ★ 抽查 |
| R3 | 动态调整 | ≥2 个依赖前序结果的分支案例 | ① 分支覆盖不同决策方向；② 计划变更有据（判据见 **§1.1**）；③ 与固定脚本路径存在可审查差异 | **plan diff + trace 回放** | ★ 参与路径审查 |
| R4 | 漏洞线索发现 | 靶场预植已知漏洞清单（6–8 个） | ① 召回率 ≥75%；② 逐条比对可复核；③ 无效调用率 ≤30%（总则-3，**按等级分账**） | 线索对照表 + 审计统计 | |
| R5 | 漏洞确认与报告 | R4 线索存在 | ① CONFIRMED 率 ≥50%；② 每条 CONFIRMED 附证据与复现步骤；③ 四态正确、效率字段齐全 | 证据文件 + 结构化报告 | ★ 抽 2–3 条回溯 |

> **R4/R5 的分子分母只在闭集成立**：清单是预植的、组件是已知的、验证手段是准备好的。
> 这不是"健全 agent"的全部能力，只是**回归基线**——它保证已知场景不退步，不保证未知场景不出错。
> 未知场景的判据在 P12。

### 1.1 R3 的证据形式

R3 的判据必须能直接从证据里读出来。trace 只显示"调了什么"，不显示"为什么"，因此以 `plan` 事件为准：

| 判据 | 怎么查 | 不通过的表现 |
| --- | --- | --- |
| 存在 `plan` 事件 | 审计里 `kind=plan` | 全程无 plan 事件 → 计划没落地 |
| 事件带 `trigger.stepId` | 每个 plan 事件的 `trigger.stepId` 非空且指向真实 step | 缺 trigger → 标 `untraced`，不计入 |
| 两次运行的 plan diff 不同 | `reconstruct --compare` 输出 plan 差异 | 两次跑出同样的 plan 且无 trigger → 是固定脚本 |
| 差异点之前的事实不同 | 对照 `divergence` 位置与前后 fact key | 事实相同却走了不同分支 → 疑似随机，不算驱动 |

**案例库（两个必须都有）**

| 案例 | 构造 | 期望可观察结果 |
| --- | --- | --- |
| 事实驱动选路 | 靶 A 只开 8080（无 fastjson 特征），靶 B 开 8090 且 Server 指 fastjson | A 的 plan 里 `cve_check` 假设 `refuted/unverifiable`；B 的里 `open` 并被执行 |
| 判定驱动改动作 | 首次 `cve_check` 返回 `INCONCLUSIVE` | 第二次调用**参数不同**（`allowedVariations` 生效），且不被 I3 拦 |

### 1.2 R5 的证据维度

四态不动，`Finding` 增加正交维度 `verificationLevel`：

| 值 | 含义 | 对应能力 |
| --- | --- | --- |
| `RISK_SURFACE` | 风险面存在（无损探测命中） | 现有 `cve_check` |
| `EXPLOIT_CONFIRMED` | 已验证可利用（受控利用） | 本期不承诺 |
| `CALLBACK_RECEIVED` | 靶已回连到 agent（证明可达性） | RA-3 |

**判据**：报告能区分"风险面存在"与"回连已验证"；`RISK_SURFACE` 不得写成"已利用"。
若坚持用第五态而非正交维度，须同步改总则-1、`report.ts`、`evidence.ts` 三处（代价见 `2规格/07` §7.5）。

## 2. MVP-1 集成验证场景

| 要素 | 内容 |
| --- | --- |
| 场景 | 对 1 个 Vulhub CVE 环境完成：授权配置 → 信息收集 → 分析规划 → 受控调用 → 结果观察 → 动态调整 → 结论 → 报告 |
| 通过条件 | ① 每环节留痕且字段完整；② ≥1 次由前序 Observation 驱动的分支决策（R3 新判据）；③ 报告四态正确 + 效率字段；④ 无效调用率按等级分账判定；⑤ 无越界调用；⑥ `trace_health` 非 `TRACE_MISSING` |
| 环境前置 | 沙箱 S1–S5 完成（WSL2 Docker + Vulhub + 真工具） |
| 冻结产出 | OQ-09：按实测调用次数 / 耗时 / token / 两本账比例冻结 |

> **与 2026-11-07 三靶场报告的关系**：那份报告的条件②是 🟡（未构造分支案例），
> 且 CVE 编号由人填入 prompt。按本文判据，它只能算"直线调用通过"，不构成 MVP-1 通过。
> 该结论已在 `design/agent-refactor/01-起因与目标.md` §1 记录。

## 3. R 项与 C 项的依赖（看这张表就知道为什么忽然失败）

| R 项 | 依赖的 C 项 | 依赖关系 |
| --- | --- | --- |
| R1 ③ 解析正确率 | C22（解析规则先行） | 解析全靠 LLM 时歧义不可控 |
| R2 ② 每次经控制层 | C13（全量白名单漏斗） | 漏斗只覆盖部分工具时该项不成立 |
| R3 全部 | C07（plan 事件带 trigger） | 无 trigger 则无法证明驱动关系 |
| R4 ③ 无效调用率 | C05（两本账）+ C12（重复分级） | 不分账时阈值无意义；不分级时探索被误判 |
| R5 ③ 效率字段 | C24（报告字段）+ C27（证据 kind） | 字段缺失即无法出报告 |
| R9 预算 | C11（两本账配额） | 单池预算会前期吃光后期 |
