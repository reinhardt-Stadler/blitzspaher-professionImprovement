## 1. 结论先说

**「折中档完工」不等于「R1–R5 全绿」。** 它是三件事同时成立：

| 层 | 判据 | 为什么是这一条 |
| --- | --- | --- |
| ① 性质 | 适用的 C 项全部成立 | 性质不成立时跑场景只会得到无法解释的失败（`00-索引` §5 原文） |
| ② 阶段出口 | 本期 7 个 P 项判 PASS | P 是"能不能进下一阶段"的闸门 |
| ③ 里程碑 | R1–R5、R7–R10 **对 T1/T2** 判 PASS 或明确的 FAIL | R 项本期"全部照常"，不因折中档豁免 |

**当前状态（2026-11-27 更新）：① 已判（23 PASS / 1 不适用）、② 已判（6 PASS / 1 证据不足）、
③ 半判（R4 待定口径）。** 明细见 [`08-P项判定.md`](08-P项判定.md)、[`09-C项判定.md`](09-C项判定.md)。

剩下三件：**P14 的测试设施**（U3 缺开关、U4 缺靶）、**R4 的口径决定**、**RA-0.5/5.2/5.3 的文档**。

## 2. 三条判定规则（照抄既有约定，不新增）

1. **范围外的项记 `NOT_APPLICABLE（本期范围外）`，不记 FAIL、不记空**（`00-索引` §6）。
2. **数值依赖未冻结 OQ 的项记 `INSUFFICIENT_EVIDENCE`**，不判 PASS 也不判 FAIL
   （`04-新增验收` P6 判据原文）。
3. **`FAIL` 只留给真缺陷**。若某项 FAIL 的根因是"支撑能力不在本期"，那是**规格问题**，
   要改规格而不是改结论——见 §4。

## 5. 必须指出的规格矛盾

R4 写的是"召回率 ≥75%"，`00-索引` §6 又写"R 项全部照常，仅对 T1/T2 生效"。
但撑起 R4 的三件事全在**全量档**：

| 需要的能力 | 包 | 范围 |
| --- | --- | --- |
| 每个 CVE 的探测规格（决定能不能验） | RA-2.2 | **全量档** |
| 组件指纹 → CVE 候选（决定该验哪条） | RA-2.4 TargetModel | **全量档** |
| 现场自造验证器 | RA-3.1 动态工具 | **全量档** |

也就是说：**折中档承诺了 R4 的 75%，却把实现它的三个包都划到了全量档。**
0/6 不是 agent 能力不足，是这个矛盾在实测里的直接体现（三层根因见
[`2026-11-25-R4召回率.md`](2026-11-25-R4召回率.md)）。

三个出路，代价从低到高：

| 方案 | 做法 | 后果 |
| --- | --- | --- |
| A. 拆分 R4 | 拆成 R4a（内置验证器覆盖的 CVE）与 R4b（未覆盖的），R4a 本期判、R4b 记 `NOT_APPLICABLE` | 口径诚实，但要改验收文档与索引 §6 |
| B. 缩小 R4 样本 | 预植清单只放 3 个有验证器的 CVE，召回率按 3/3 判 | 数字好看，但等于"只考做过的题" |
| C. 把 2.2 拉回本期 | RA-2.2 只做 6 个靶的探测规格 | 范围扩大，与"17 包"的既定决定冲突 |

臣倾向 **A**：它不粉饰也不扩大范围，而且 R4b 的 0/6 恰好是"为什么要转全量档 2.2/2.4/3.1"的最好证据。
**但这改的是验收口径，必须由陛下定。**
