## 二、R3：从"零 plan 事件"到"形式满足"

### 原诊断（修正前）

三次运行 `decision 10/9/9、execution 9/9/9`，**零 `plan`、零 `hypothesis`**。
`index.ts:238` 的 `mirrorToAudit` 已写好且 `feed()` 会调它——审计侧接线在，
但 `ev.type === "plan_change"` 从未触发。

**根因**：宿主只 feed `tool_call_started` / `tool_result` / `policy_confirmed` / `user_command`，
**从不喂 `hypothesis_proposed`**。而 `plan_change` 由 `hypothesis_proposed` 等输入产生，
于是整条假设/计划链路在真实循环里是死的。`tool_call_started` 的 `hypothesisId` 恒为 `null`。

### 修复

1. `KernelInput.hypothesis_proposed` 增加 `stepId`，内核用它填 `trigger.stepId`
   （原本写死 `null` 并标 `untraced`，而 R3 判据明确要求 trigger 指向真实 step）
2. 宿主在 `tool_call_started` 前建模假设：用已积累的事实作 basis（内核拒空 basis），
   并把当前调用关联到 `hypothesisId`

### 实测（两靶对比，T2：只给目标不给 CVE）

| | A 靶 shiro 8080 | B 靶 fastjson 8090 |
| --- | --- | --- |
| 结论 | 0 项确认，正确上报验证器缺口 | **CONFIRMED fastjson** |
| 假设 basis | `host:127.0.0.1`, `path:/:302` | `host:127.0.0.1`, `path:/:200` |
| plan 变更 | 10 个（step 4/15/19/…/55） | 8 个（step 4/19/23/…/45） |
| trigger.stepId | 全部非空 | 全部非空 |

**R3 四条判据**：① 存在 plan ✅ ② trigger.stepId 非空 ✅ ③ 两次 diff 不同（数量与 step 序列）✅
④ 差异点之前的事实不同（`path:/:302` vs `path:/:200`）✅

### 但有一个弱点，必须写明

**两次假设的 `statement` 是同一个文本**（`探测 127.0.0.1（nmap_scan）`），因为建模时机在首次调用，
那时还没有 service/version 事实。diff 的差异主要来自**执行步数不同**，不是"计划内容不同"。

此外 10 个 plan 更新里 9 个的 reason 都是"已识别组件但无可用验证手段"——
这是 `onNoProbeSpec` 的缺口上报，不是模型的计划调整。**plan 事件变成了缺口日志**。

改进方向（未做）：当发现新组件（service/version 事实）时建新假设，
让 statement 反映"发现的是什么"（Spring Security vs fastjson），两靶的假设内容才会真正分叉。

## 三、R4③ 的 40% 是怎么来的

修正判据后逐条归因（`R1-T1-final`）：

| 调用 | 判定 | 原因 |
| --- | --- | --- |
| `env_selfcheck` | excluded(X2) | 自检不产事实，属口径错配 |
| `http_probe` | valid | |
| `nmap_scan` | deny → 重发 valid | 首次端口跨度 1001>1000 被拦（策略正确） |
| `knowledge_query` ×2 | excluded(X1) + I1 | 首次能力缺失豁免，第二次重试记 I1 |
| `knowledge_read` ×2 | excluded(X2) | 读文档不产目标事实 |
| `cve_lookup` | excluded(X2) | 查情报不产目标事实 |
| `cve_check` | valid | |

无效 2 = 两次"知识库缺失后仍继续查"。分母 5，**40%**。

两个必须说清的点：

1. **阈值不存在**。`3验收/01` 总则-3.1 写明"按等级分别冻结"，数值待 OQ-09 首次试跑后定。
   所以严格说是"实测 40%，无法判达标与否"，不是"不达标"。
2. **40% 全部来自重试**。若 agent 在首次 `capability_gap` 后不再重试，无效率为 0。
   这指向 §6.7 的缺口上报还没真正影响决策——上报了，但模型没据此止损。

## 四、本轮修掉的 5 个缺陷

验收的价值在这里：854 项单测全绿，但真跑一次暴露 5 个问题，其中 3 个会让**报告说假话**。

| # | 位置 | 缺陷 | 后果 |
| --- | --- | --- | --- |
| 1 | `reconstruct.ts` CLI | 只给 jsonl 路径时 `auditDir` 回落默认目录 | 日志读得到、observation 全找不到 → `TRACE_MISSING`，正确运行被读成"没留痕" |
| 2 | `evidence.ts` | 没有"能力缺失"与"不产事实"的豁免 | 库缺失、自检、知识检索全被算成无效调用，无效率虚高 |
| 3 | `evidence.ts` `extractFacts` | 对**所有工具**取 `evidence.url` 的 host | `cve_lookup` 查 NVD 时把 `services.nvd.nist.gov` 记成"目标 host"，事实台账与"触达目标"被污染 |
| 4 | `evidence-collector.ts` | tar 用绝对 Windows 路径 + `-C` | GNU tar 把盘符当远程主机，**证据包永远产不出**（R5 硬伤） |
| 5 | `tools.ts` knowledge 类 | 缺 `producesFacts:false` | 正确的知识查询被判"无新增事实" |

修后验证：`TRACE_COMPLETE`、证据包产出 sha256 `b527ddce…`、无效率从 55.6% → 40%（剩余为重试）。
