## 1. 执行方式（可复现）

```bash
# 宿主侧：重建镜像载入全量档代码
node deploy/prepare-build.mjs
cd deploy && docker compose build agent && docker compose up -d --no-deps agent
# 容器内：pi 1.5 的 --print 不接行内 prompt，必须用 stdin
printf '%s' "$PROMPT" | docker exec -i bz-agent sh -c '
  unset TMPDIR TEMP TMP XDG_CONFIG_HOME XDG_CACHE_HOME XDG_DATA_HOME LOCALAPPDATA APPDATA PWD OLDPWD
  export HOME=/tmp PENTEST_RUN_ID=... PENTEST_AUDIT_DIR=... PENTEST_OUTPUT_DIR=/work/out-1128
  cd /app/pi-pentest
  pi -p -e ./src/index.ts -ne -nbt --no-session --model deepseek/deepseek-v4-pro \
     --append-system-prompt /work/agent-persona.md'
```

三个必须清掉的环境变量：`TMPDIR`（宿主 Windows 路径拼进容器报错）、`PWD`（宿主 Git Bash 路径
导致输出目录解析到 `D:/workbuddy/...`）、`XDG_*`（pi 配置目录）。

### 4.2 召回率

按"预植 CVE 被正确确认"计：**2/5 = 40%**（可判定的 5 靶；drupal 因授权记 NOT_EXECUTED 不入分母）。
按"正确识别组件并调用预植 CVE 的 `cve_check`"计：**5/6 = 83%**（drupal 除外全部命中）。
后者说明 RA-2.2 / 2.4 的组件→CVE 链路已生效；前者说明验证器覆盖仍是瓶颈。
**口径与上次 0/6 不完全可比**：上次六靶里 3 靶根本没调 `cve_check`，这次 5 靶都调了。

### 4.3 与上次相比的变化

- 上次 3 靶"完全没调 `cve_check`"→ 本次只有 1 靶（drupal，且是授权拒绝）。
- 上次 2 靶"猜错组件"→ 本次 0 靶；两靶确认了别的 CVE，但组件识别是对的。
- 全量档的 `cve_lookup` 在线查询、`probe_forge`、`callback_watch` 能力在本轮**未授予**，
  所以"无内置验证器的 CVE"仍无法现场造验证器——这不是缺陷，是授权边界。
